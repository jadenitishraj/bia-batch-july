01

Why Models Get Things Wrong

Before the five techniques, one fact about how a model writes an answer. Once you understand this fact, all five techniques become obvious.

The model writes one word at a time, and it never goes back

Ask a model a question and it starts writing immediately. The very first word it writes is already part of the answer. It has not worked anything out yet. It has written the word that usually comes next — and now the rest of the answer has to agree with that word.

Your question
→
First wordalready guessing
→
Rest of the answerhas to agree
→
Sounds confidentmay be wrong
No rough paper · no going back · no way to check a fact

Think about how you would answer a hard question. You would use rough paper. You would try one idea, see it was going nowhere, and try another. You would look something up. Those three habits are the four techniques in this deck.

The four things that go wrong

PROBLEM 1It skips the working
SituationYou are reviewing a pull request. It changes 4 files. Each file has 3 functions, and each function needs 2 tests. Two of the tests already exist.
We wantThe number of new tests to write. The correct answer is 22.
✗Wrong approach
How many new tests do we need?
Give me just the number.
What comes back
24
Wrong, and it looks very sure of itself. There was nowhere in the answer to write "4 × 3 = 12" or "12 × 2 = 24" or "24 − 2 = 22", so the model never wrote those numbers — and never used them.
✓Right approach
Work it out in this order, one line each:
1. total functions
2. tests needed in total
3. subtract the tests we already have

Then write the final number on its own
line, starting with ANSWER:
What comes back
1. 4 × 3 = 12 functions 2. 12 × 2 = 24 tests 3. 24 − 2 = 22 ANSWER: 22
Same model, same question. We just gave it space to write the middle numbers. Each line can now use the line above it.
Lesson
The words the model writes are its rough paper. No room in the answer for the working means there was no working. This is fixed by Chain of Thought.
PROBLEM 2It sticks with its first idea

Ask "how should we store user sessions?" and you will get one answer. It will be the first idea that came to mind. The model never compared it against anything, because by the time it had written three words it was already committed. Asking it to "think step by step" does not help here — it just walks further down the same road.

Fixed by Tree of Thought: make it produce three different options, score each one, then pick.

PROBLEM 3It cannot combine several pieces of work

You ask it to read six research papers and write one summary. If you paste all six in at once, the middle ones get ignored. If you feed them one at a time, the last one dominates. What you actually want is a summary of each paper, then those summaries combined carefully — keeping every finding, and keeping the places where two papers disagree.

Fixed by Graph of Thought: do the pieces separately, then merge them with clear rules.

PROBLEM 4It makes up facts it cannot know
SituationA test called test_checkout_totals is failing in your project. You ask the model why.
We wantThe real reason, based on the real error message.
✗Wrong approach
Why is test_checkout_totals failing?
Think step by step.
What comes back
Step 1: The test checks the cart total. Step 2: Totals usually break when tax is applied twice. Step 3: So the tax is likely being added in both add_item and get_total. Fix the double tax calculation.
Every step is neat. Every step is invented. The model has never seen your code or your error message. Step-by-step thinking on top of made-up facts gives you tidy nonsense, which is worse than "I don't know" because it looks checked.
✓Right approach
You can use these tools:
  run_test(name)
  read_file(path)

Rules:
· Run the test first. Read the real error.
· Never say anything about the code that
  you have not read.
What comes back
Ran test_checkout_totals Error: TypeError: unsupported operand type(s) for +: 'int' and 'NoneType' at cart.py line 41 Read cart.py lines 30-50 Line 41 adds item.discount, which is None when no discount is set. Fix: use (item.discount or 0)
Shorter, less clever, and it is the only version that is actually true. Every sentence points at something the model really saw.
Lesson
Better thinking cannot create a fact the model never had. If the answer lives in your files or your database, the model has to go and look. This is fixed by ReAct.

Chain Of Thought — Show The Working

The simplest of the five, and the one you will use most. One idea: make the model write the middle steps before it writes the answer.

What problem does it solve?

The model has no rough paper. Everything it "knows" while answering is the text it has already written. So if the answer needs three steps and you only asked for the final number, those three steps never happened.

Chain of Thought fixes this by making the steps part of the answer. Step 2 can then read step 1. Step 3 can read step 2. That is the whole idea.

Question
→
Step 1
→
Step 2
→
Step 3
→
Answer
One straight line · one model call · the answer comes last

Read it like this: the model writes step 1, then reads its own step 1 to write step 2, and so on. The answer is written last, when all three steps are already on the page in front of it.

How to use it — three ways, from cheapest to most expensive

Way 1
Just ask for steps
Add Think step by step. to the end of your prompt. Free, takes two seconds, and often enough.
Way 2
Name the steps yourself
Write out steps 1 to 5 in the prompt. Same cost, much more reliable, and you can check the model did all five.
Way 3
Ask five times and vote
Run the same prompt 5 times, take the most common answer. Five times the cost, and the best accuracy you can buy cheaply.
EXAMPLE 1Finding a bug in a small function
SituationA teammate wrote a function that should return the last 3 items of a list. It works on long lists. It crashes on short ones.
We wantThe model to find the bug and say which input breaks it.
Why it is hardThe bug only shows up for one specific input. Reading the code and "feeling" that it is fine is not enough — you have to actually run it in your head.
✗Wrong approach
Is there a bug in this function?

def last_three(items):
    return items[len(items)-3:]
What comes back
This function looks correct. It uses len(items)-3 as the starting index to slice the last three elements, which is a standard Python pattern.
The model gave an opinion, not a check. It never tried a single input. There is a real bug: when the list has 2 items, len(items)-3 is -1, so it returns only the last item instead of both.
✓Right approach
Check this function by hand.

def last_three(items):
    return items[len(items)-3:]

For each of these inputs, write the
value of len(items)-3, then what the
slice returns, then whether it is
correct:
  [1,2,3,4,5]
  [1,2,3]
  [1,2]
  []

Then say BUG or NO BUG on the last line.
What comes back
[1,2,3,4,5] → 2 → [3,4,5] → correct [1,2,3] → 0 → [1,2,3] → correct [1,2] → -1 → [2] → WRONG, should be [1,2] [] → -3 → [] → correct BUG
We did not ask it to be cleverer. We gave it four inputs and a table to fill in. The bug appears in row three because the model had to write down the number -1.
Lesson
Do not ask "is this correct?". Ask the model to run specific inputs and write down what happens. Opinions are cheap; a filled-in table is checkable.
EXAMPLE 2Putting the answer in the wrong place
SituationYou are building a tool that reads code review comments and labels each one blocking or minor. It returns JSON so your app can use it.
We wantThe right label. The comment is: "This works, but I would rename the variable." That is minor.
Why it is hardNothing at all looks wrong with the first prompt. This is the most common Chain-of-Thought mistake in real code.
✗Wrong approach
Return JSON:
{
  "label": "blocking" or "minor",
  "reason": "..."
}
What comes back
{ "label": "blocking", "reason": "The reviewer is asking for a change before merge." }
JSON keys come out in the order you wrote them. So label is decided first, with no thinking behind it. Then reason is written to justify a decision that has already been made. The reason field is doing nothing.
✓Right approach
Return JSON with the keys in exactly
this order:
{
  "quote": "the words that decide it",
  "reason": "...",
  "label": "blocking" or "minor"
}
What comes back
{ "quote": "This works, but", "reason": "The reviewer says the code works. A rename is a preference, not a defect.", "label": "minor" }
Exactly the same three fields. We only moved the label to the bottom. Now the quote and the reason are already written when the label is chosen, so they actually affect it.
Lesson
Always put the answer last. In a prompt, in a JSON schema, in a report — anywhere. If the conclusion comes out before the reasoning, the reasoning is just an excuse written afterwards.

Chain Of Thought — Two More Examples

One from research, one that shows how to buy extra accuracy when the answer really matters. Then where to use this, and a summary.

EXAMPLE 3Checking whether a paper supports your claim
SituationYou are writing a report. You want to say "remote teams ship faster" and cite a study. You have the study's abstract in front of you.
We wantAn honest yes or no. The study actually measured hybrid teams, not remote ones, and it measured satisfaction, not speed. So the honest answer is no.
Why it is hardThe model wants to be helpful. If you ask "does this support my claim?", it will find a way to say yes.
✗Wrong approach
Does this study support the claim
that remote teams ship faster?

[abstract pasted here]
What comes back
Yes, this study provides support for the claim. It found positive outcomes for teams working outside a traditional office, which is consistent with the idea that remote teams perform well.
"Consistent with the idea that" is the model being polite. You put the answer in the question, so it agreed with you. If you cite this in your report, a reviewer will check the study and you will look careless.
✓Right approach
Answer these in order. Quote the
abstract for each one.

1. Who exactly did they study?
2. What exactly did they measure?
3. What was the result, with numbers?
4. My claim is "remote teams ship
   faster". Does 1 match "remote"?
   Does 2 match "ship faster"?
5. Only now: SUPPORTS / DOES NOT
   SUPPORT / PARTLY. One line why.
What comes back
1. "142 hybrid teams (2-3 office days)" 2. "self-reported job satisfaction" 3. "+11% satisfaction vs fully office" 4. Hybrid is not remote. Satisfaction is not shipping speed. 5. DOES NOT SUPPORT — wrong population and wrong outcome measure.
Steps 1 to 3 are just facts copied from the page. Step 4 compares them to your claim. Only step 5 gives a verdict — and by then the honest answer is the only one left.
Lesson
Never put your desired answer inside the question. Make the model write down the facts first, then compare, then judge.
EXAMPLE 4Asking five times and taking the most common answer
SituationA database query in a pull request looks wrong. If it is wrong, the monthly report will double-count revenue. Nobody on the team is sure.
We wantA yes or no, plus some idea of how confident we should be.
Why it is hardThe model always sounds confident. Asking it "how sure are you?" gives a number that means nothing.
✗Wrong approach
Does this query double-count?
Also tell me how confident you are
out of 10.
What comes back
No, the query does not double-count. Confidence: 9/10
That 9 is not measuring anything. Models say 8 or 9 for almost everything, whether they are right or wrong. You have learned nothing.
✓Right approach
# same prompt, run 5 times,
# temperature 0.7 so the runs differ
answers = []
for i in range(5):
    out = ask(prompt, temperature=0.7)
    answers.append(out.split("ANSWER:")[-1])

winner, votes = most_common(answers)
# votes tells you how sure to be
if votes < 4:
    send_to_human(winner, votes)
What comes back
run 1 → double-counts run 2 → double-counts run 3 → fine run 4 → double-counts run 5 → double-counts winner: double-counts (4 of 5) → good enough to act on
The vote count is the confidence, and this one is real. 5 out of 5 means the question was easy. 3 out of 5 means send it to a human. This works because a wrong answer can be reached many different ways, but the right one usually only one way.
Lesson
Temperature must be above 0 or all five runs are identical and the vote means nothing. Keep the vote count — most people throw it away, and it is the most useful part.

Where to use Chain of Thought

Use case 1
Reviewing code for bugs
Give it three or four specific inputs and make it trace what the function returns for each. Far better than "does this look right?".
Use case 2
Working out anything with numbers
Cost estimates, how many API calls a loop makes, storage sizes, invoice checks, marks and grades. One line per calculation, total at the end.
Use case 3
Applying rules that are written down
Refund policy, leave entitlement, whether a PR meets the merge checklist. Go through the rules in order and say which one decided it.
Use case 4
Reading an error message
Which line threw it, what value was wrong, which caller passed that value, what to change. Each step feeds the next.
Use case 5
Checking a source in research
What was studied, what was measured, what was found, does that match my claim. Facts first, verdict last.
Use case 6
Marking work against a rubric
Score each criterion with a quote as evidence, then add up. The student can then argue with one criterion instead of the whole grade.

When not to use it

✗
Simple lookups"What port does Postgres use?" Steps add cost and time and change nothing.
✗
Creative writingPlanning a poem step by step gives you a correct, boring poem.
✗
Anything that must be fastAutocomplete, live typing. Three times the words on every keystroke gets expensive.
✗
When the model has no factsIt will fill the gaps with invention, and the steps make the invention look verified.
Summary — Chain of Thought
Four things to take away
  1. What it is: make the model write the middle steps before the answer, so each step can use the one above it.
  2. The one rule: the answer always comes last. In prompts, in JSON, everywhere.
  3. Name the steps yourself instead of just saying "think step by step". Then you can check it did all of them.
  4. When it really matters, run the prompt 5 times and take the most common answer. Keep the vote count as your confidence.
Your labelling tool returns {"label": ..., "reason": ...} and gets 71% right. You move one line and it gets 84% right. What did you move?
With label first, the model picks a label and then writes an excuse for it. Move reason above and the thinking is on the page before the label is chosen. Same fields, one line moved.

Tree Of Thought — Try Three, Keep The Best

Chain of Thought walks down one road. If that road is wrong, you just get a very well-explained wrong answer. Tree of Thought walks down three roads and compares them.

What problem does it solve?

Ask a model "how should we store user sessions?" and it starts typing an answer straight away. Whatever idea came out first is now the answer. It never compared that idea against anything, because there was nothing to compare it with.

Tree of Thought fixes this in three moves: make three different options, give each one a score, throw away the bad ones, and look more closely at the good ones.

Read it like this: the question at the top splits into three different ideas. Each idea gets a score. Option A scores badly, so we stop working on it — that is called pruning. The other two get one more question each, and get scored again. The highest score wins. Notice that we also end up with a written reason for rejecting A and B, which is often the most useful part.

The three things you have to write yourself

Part 1
A prompt that makes options
"Give me 3 different approaches." You must say different, or you get the same idea worded three ways.
Part 2
A prompt that scores one option
A separate call, one option at a time. It must not know what the other options were.
Part 3
A limit
Stop after 3 levels, or 40 calls, or 60 seconds. Without a limit this runs until someone notices the bill.
Do the maths before you build this

3 options at each of 3 levels, keeping the best 2 each time, is about 30 model calls for one answer. That is fine for "which database should we use". It is not fine for "label this support ticket".

EXAMPLE 1Choosing between three designs
SituationYour team is adding a feature that emails a user when their order ships. You need to decide how to send those emails.
We wantA decision, plus the reason the other options were rejected — because that is what your tech lead will ask for.
Why it is hardThere is no single right answer. Three sensible engineers would pick three different things, and the right one depends on your team.
✗Wrong approach
How should we send the shipping
confirmation email?
What comes back
Use a background job queue. When the order status changes to "shipped", push a job onto the queue and have a worker send the email through your email provider. This keeps the web request fast and gives you retries.
A perfectly reasonable answer, and you have no idea whether it is the best one. Nothing was compared. If your team has never run a queue, this may be the worst choice available.
✓Right approach
# call 1 — make the options
"Give me 3 genuinely different ways to
 send this email. Different approach,
 not different wording. Argue for each
 one equally. Do not pick a favourite."

# calls 2, 3, 4 — score them one by one
"Score this ONE option from 0 to 1 on:
  reliability: 1 = the email always
    arrives even if the provider is down
    0 = one failure loses the email
  effort: 1 = ships this week with what
    we already run
    0 = we must add new infrastructure
 Give the number and one line of why."

# call 5 — your code picks the winner
best = max(options, key=score)
What comes back
A send it inside the web request reliability 0.2 effort 1.0 B background job queue reliability 0.9 effort 0.4 (we do not run a queue today) C write a row to an "outbox" table, a cron job sends it every minute reliability 0.8 effort 0.8 CHOSEN: C Rejected A: one provider outage silently loses the email. Rejected B: new infrastructure.
Option C never appeared in the first version, and it is probably the right answer for a small team. It only exists because we asked for three different approaches.
Lesson
Scoring needs anchors — you must say what 0 and 1 actually mean. Without them the model gives everything 0.7 and the scores are useless.
EXAMPLE 2Asking for options and a winner in the same message
SituationSame job as example 1, but you try to save time by doing it in one call instead of five.
We wantA fair comparison of three options.
Why it is hardThe model writes left to right. Once it has written option 1 and called it good, options 2 and 3 are written knowing they are meant to lose.
✗Wrong approach
Give me 3 options and tell me
which one is best.
What comes back
1. Background job queue (recommended) 2. Send it in the web request 3. A third-party automation tool Option 1 is best because it is the industry standard approach.
Options 2 and 3 were written to lose. They are weak on purpose. And "industry standard" is not a reason — it is a way of not giving one. One call cannot both invent options and judge them fairly.
✓Right approach
# call 1 — options only
"Give me 3 different options.
 Argue for each one equally strongly.
 Do NOT say which is best."

# calls 2-4 — a fresh, empty
# conversation for each option
"Here is one option. Score it against
 this rubric. You are not comparing it
 to anything else."

# then your code picks the highest score
The scorer never sees the other options, so it cannot be swayed by the order they were written in. Keep the option-maker and the judge apart.
Lesson
If the same message both invents an option and rates it, the rating is worthless. It costs three extra calls to do it properly. Do the three extra calls.

Tree Of Thought — Two More Examples

One where the computer does the scoring for you, one where the options only look different. Then where to use it, and a summary.

EXAMPLE 3Letting the tests decide which fix is right
SituationOne test is failing: test_discount_on_empty_cart. There are several ways to fix it. Some of them will break other tests.
We wantA fix that makes the failing test pass and keeps all 214 other tests passing.
Why it is hardA fix can look completely sensible and still break something three files away. Reading it is not enough.
✗Wrong approach
Give me 3 possible fixes, then score
each one from 0 to 10 on how likely
it is to work.
What comes back
Fix 1: guard against empty cart — 8/10 Fix 2: default the discount to 0 — 8/10 Fix 3: return early in get_total — 7/10
Three numbers that are all basically the same, produced by a model that has not run anything. You still have to test all three yourself, so the scoring step added nothing but cost.
✓Right approach
# 1 - ask for 3 different fixes
fixes = ask("3 different fixes for this
             failure. Different approach,
             not different formatting.")

# 2 - the SCORE is the test run.
#     no model opinion involved.
for f in fixes:
    apply(f)
    result = run_all_tests()
    f.score = result.passed
    revert(f)

# 3 - keep only fixes with a full pass
best = [f for f in fixes
        if f.score == 215]
What comes back
Fix 1 215/215 passed ✓ Fix 2 213/215 passed ✗ (broke 2 bulk-order tests) Fix 3 215/215 passed ✓ 2 fixes work. Show both to the human with the diff.
No opinions anywhere. The test suite gave an exact score for each option, and it found that fix 2 quietly breaks two other tests — something no amount of reading would have caught.
Lesson
If you can actually run the options — tests, a compiler, a schema check, a query against real data — do that instead of asking a model to guess. This is the best version of Tree of Thought there is.
EXAMPLE 4Options that are only reworded
SituationYou are starting a research project on why users abandon your signup form. You want several angles to investigate, not just one.
We wantThree approaches that would find genuinely different things.
Why it is hard"Give me 3 options" almost always returns one idea written three ways. The tree then has three branches that all lead to the same place.
✗Wrong approach
Give me 3 ways to research why users
abandon our signup form.
What comes back
1. Survey users who dropped out 2. Send a questionnaire to people who did not complete signup 3. Ask abandoned users for feedback
These are the same idea three times. You have three branches with a real branching factor of one, and you are paying three times to explore one road.
✓Right approach
Give me 3 research approaches, each
using a DIFFERENT source of evidence:
 1. something users SAY  (interviews,
    surveys)
 2. something users DO   (analytics,
    session recordings)
 3. something the SYSTEM records
    (error logs, timing data)

Two approaches using the same source
is not allowed.
What comes back
1. SAY — interview 8 users who dropped at the password step 2. DO — funnel analysis: which field is the last one they touch 3. SYSTEM — count validation errors per field in the last 30 days (3 found that 41% of drop-offs follow a password rule error the user never sees. None of the other two would have found that.)
You have to name the thing that must differ. Here it is the source of evidence. In example 1 it was the technical approach. Difference never happens on its own.
Lesson
Say what makes the options different — a different source, a different technology, a different assumption. Otherwise you are paying for three copies of one answer.

Where to use Tree of Thought

Use case 1
Design and architecture decisions
Which database, which queue, monolith or services, how to store sessions. Expensive to change later, so 30 calls is cheap.
Use case 2
Fixing a bug when the tests can judge
Generate several fixes, run the whole suite on each, keep the ones that pass everything. The score is free and exact.
Use case 3
Writing test cases
Branch on types of failure — empty input, huge input, wrong type, no permission, two users at once — then write cases under each.
Use case 4
Working out why something broke
List four possible causes — the deploy, a dependency, the data, capacity — and for each, what evidence would prove or kill it. Stops you fixating on the first idea.
Use case 5
Planning a research project
Three approaches using different evidence, scored on how fast and how convincing each would be.
Use case 6
Naming things, and writing copy
Branch on the angle — the problem, the outcome, the price, the comparison — not on the wording. Several good answers genuinely exist.
Use case 7
Timetables and rosters
Each branch places one person or one class. The score is the number of rules broken, which a small function can count exactly.

When not to use it

✗
There is only one right answerPulling a date out of a document. Nothing to compare, so nothing to search.
✗
You cannot say what a good answer looks likeIf you cannot write the rubric, the scores will be noise. Stay on Chain of Thought.
✗
High volume or fast responses needed30 calls per item does not survive contact with real traffic.
✗
You have not tried the cheap versionFive runs and a vote costs a sixth as much. Try that first.
Summary — Tree of Thought
Four things to take away
  1. What it is: make three different options, score each one, drop the bad ones, look closer at the good ones.
  2. Keep the maker and the judge apart. One call makes options, separate calls score them one at a time.
  3. Use a real check when you have one — a test run, a compiler, a rule counter — instead of asking a model to rate things.
  4. Always set a limit on depth, calls and money, and keep the rejected options with their reasons. That list is half the value.
You built a tree to choose a caching strategy. Every option scores between 0.7 and 0.8, and a different one wins every time you run it. What is wrong?
If you just say "rate this out of 10", a model gives 7 or 8 to anything that sounds sensible. Your search is then sorting random noise, which is why the winner keeps changing. Say what 0 means and what 1 means on each thing you are scoring.

Graph Of Thought — Combine The Pieces

A tree makes you pick one winner. Sometimes you do not want a winner — you want all of it, joined together properly. That is the job Graph of Thought does.

What problem does it solve?

You have four research papers and you need one summary. There are three obvious ways to do it, and all three are bad:

  • Paste all four in at once. The model pays attention to the first and the last. The two in the middle get thin treatment.
  • Feed them one after another. Paper 1 gets squashed four times and disappears. Paper 4 gets squashed once and dominates.
  • Use a tree and pick the best summary. Nonsense — you wanted all four, not the best one.

What you actually want is: summarise each paper on its own, then join the summaries together in pairs, so every paper goes through the same number of steps and gets the same weight. That is all Graph of Thought is.

Read it like this, from the top. Each paper is read on its own, so no paper gets ignored. Then notes 1 and 2 are joined into one set, and notes 3 and 4 into another. Then those two sets are joined. Every paper has now been through exactly two joins, so all four carry equal weight — that is the whole reason for doing it in pairs. Finally the joined notes become a draft, which gets checked and improved a few times and then stops.

The two moves a tree cannot do

Move 1
Join
Two results become one. A tree can only choose between two results — it can never combine them.
Move 2
Improve in place
One result gets checked and rewritten, over and over, until it is good enough or you run out of tries.
And
This is code, not a prompt
You write a small program. Each box in the picture is one model call. The arrows are just the order you call them in.
EXAMPLE 1Joining two sets of notes without losing anything
SituationYou are writing a report on how users feel about your new signup flow. You have notes from two sources. Source A is a survey: satisfaction score is 62 out of 100. Source B is your analytics: 40% of users give up on step 3.
We wantJoined notes that still contain both numbers, and that flag the fact that these two findings point in opposite directions.
Why it is hardThis join will happen again at the next level, and the level after. Anything lost here is lost forever, and the losses pile up.
✗Wrong approach
Combine these two summaries into one.
What comes back
Users are broadly satisfied with the signup flow, although some report friction during the process.
Both numbers are gone. The word "some" replaced "40%". And the most interesting thing in the whole report — that your survey and your analytics disagree — has been smoothed into a sentence that says nothing. Do this three times and there is nothing left.
✓Right approach
Join these two lists of findings.
Follow these rules exactly:

· Keep every finding. Never drop one.
· Never change a number.
· Never use words like "some", "many"
  or "broadly" to replace a number.
· If two findings say the same thing,
  keep one and list both sources.
· If two findings disagree, keep BOTH,
  mark "disagree": true, and write one
  line saying what the disagreement is.

Return a JSON list only.
What comes back

Both numbers survived. Both sources are recorded. And the disagreement is now an item in the report instead of something that quietly vanished. This can be joined again five more times and still hold its shape.
Lesson
Join lists of findings, not paragraphs. Every join over paragraphs throws away detail, and you are about to do it several more times. A list with a source on each item survives.
EXAMPLE 2When two sources give different numbers
SituationYou are pulling together a quarterly summary. The finance sheet says revenue was up 12%. The analytics dashboard says it was down 3%. Both are for Q3.
We wantThe report to say clearly that the two systems disagree, so somebody goes and finds out why.
Why it is hardA model asked to "reconcile" two numbers will find a middle-sounding phrase. That is the worst possible outcome — it hides a real problem.
✗Wrong approach
Reconcile these two findings.
What comes back
Revenue grew moderately in Q3.
"Moderately" is a number that appears in neither source. Nobody can defend it, nobody can check it, and the fact that two of your systems disagree about revenue — which somebody urgently needs to look at — has been deleted.
✓Right approach
Compare these two findings using these
rules, in this order:

1. Different time periods? Keep both,
   label each with its period.
2. Same period, different number?
   Mark it CONFLICT. Keep both numbers.
   Name both sources. Do not average
   them. Do not soften the wording.
3. One source is more than 90 days old?
   Keep both, mark the older one stale.

Never invent an explanation for the
difference.
What comes back
CONFLICT — Q3 revenue finance sheet: +12% analytics dashboard: −3% Both cover Jul-Sep. Needs a human to find out which is right.
Now the report tells you something useful. A disagreement between two systems is a finding, not a formatting problem — and it is usually the most valuable line in the document.
Lesson
Write the rules for what to do when sources disagree, and put them in order. Averaging two numbers you cannot explain gives you a figure that exists nowhere and that nobody can stand behind.

Graph Of Thought — Two More Examples

EXAMPLE 3Joining four separate code review passes
SituationA large pull request. You run four separate review passes so each one can concentrate: bugs, security, performance, style. Each pass returns its own list.
We wantOne review for the author. Same issue found twice should appear once. Two passes that disagree should both be shown.
Why it is hardThe bug pass and the performance pass often both flag line 88 — but for opposite reasons. "Add a lock here" and "this lock is why it is slow" must not be silently merged into one bland comment.
✗Wrong approach

Merge them into one clean review.
What comes back

Twenty-three specific findings became four vague sentences with no file names and no line numbers. The author cannot act on any of it. And the real conflict — two passes wanting the opposite thing on line 88 — is now the phrase "consider reviewing the locking approach".
✓Right approach
Join these four lists of findings.

· A finding is the same as another only
  if the file AND line match. Then keep
  one, and list which passes found it.
· If two findings are on the same line
  but ask for OPPOSITE changes, keep
  both and mark "needs_decision": true.

· Keep every file:line. Never summarise.

What comes back

Nineteen unique findings, four duplicates removed, and one line flagged as needing a human decision because two passes want opposite things. That flag is the single most useful output of the whole review.

Say exactly what "the same finding" means — here it is file + line. Without that rule the model merges things that only sound similar, and you lose real detail.
EXAMPLE 4The improve-it-again loop that never stops
SituationYou have a draft report. You want the model to check it and improve it, the way you would revise your own work.
We wantA better draft, and for the program to actually finish.
Why it is hardIf you ask a model "what could be better here?", it will always find something. There is no point at which it says "nothing, this is fine".
✗Wrong approach
while True:
    notes = ask("What could be improved
                 about this draft?")
    draft = ask("Rewrite it using
                 these notes.")
What happens
round 1 "it is too long" round 2 "now it is too short" round 3 "add some examples" round 4 "it is too long" round 5 "now it is too short" ... forever
Two problems. There is no way to stop, and the critic has no standard to judge against, so it just swings between two complaints. Forty minutes later it is still going and the draft is no better than round one.
✓Right approach
# the critic prompt has a standard
# and a cap on how much it may say:
CRITIC = """Score this draft 0-1 against
the checklist. Then list ONLY problems
that make it unusable. Maximum 3.
If there are none, output NONE.
Do not suggest style preferences."""

best, best_score = draft, 0
for i in range(3):                 # cap
    c = ask(CRITIC, draft)
    if c.score >= 0.85: return draft   # good enough
    if c.score <= best_score: break    # not improving
    best, best_score = draft, c.score
    draft = ask("Fix only these:", c.problems)
return best        # the best one, not the last one
What happens
round 1 score 0.62 → 2 problems round 2 score 0.81 → 1 problem round 3 score 0.88 → good enough returns round 3's draft
Four things were added: a checklist to score against, a good enough threshold, a hard cap of three rounds, and a stop if it is getting worse. And it returns the best draft it saw, not the last one — the last round is often worse than the one before.
Lesson
Any loop where the model improves its own work needs all four: a score, a "good enough" line, a maximum number of tries, and a memory of the best version so far. Leave one out and it either never stops or hands you its worst attempt.

Where to use Graph of Thought

Use case 1
Summarising many documents
Ten papers, twenty interview transcripts, a folder of reports. Read each on its own, join in pairs, keep every finding and every source.
Use case 2
Literature reviews

Summary — Graph of Thought
Four things to take away
  1. What it is: do the pieces separately, then join them in pairs so every piece carries the same weight.
  2. Join lists, not paragraphs. Each item keeps its number and its source. Joining prose loses detail every single time.
  3. Write the rules for disagreement. When two sources conflict, keep both and mark it. Never average, never soften.
  4. Any improve-it-again loop needs four brakes: a score, a good-enough line, a maximum number of rounds, and keeping the best version seen.
You join ten documents and the final summary says almost nothing useful. What is the fix?
Every time you ask a model to combine two paragraphs, it drops the specifics and softens anything that disagrees. Do that three levels deep and most of your detail is gone. A bigger model just does it more elegantly. Join structured items, each with its number and its source, and write down what to do when two of them clash.

ReAct — Let It Look Things Up

The first three techniques all think inside a closed room. ReAct opens a door. The name is short for Reason and Act: think about what you need, go and get it, read what actually came back, think again.

What problem does it solve?

The model does not know your code, your database, today's date, or anything that happened after it was trained. If you ask a question that depends on any of those, it will make something up — and it will sound completely certain while doing it.

ReAct fixes this by giving the model a small set of things it can actually do — read a file, run a test, search the code, query a table — and then running a loop.

Read it like this: the model writes one sentence about what it needs, then calls one tool. Your program runs the tool and pastes the real result back in. The model reads that result and decides what to do next. The middle box is the important one — without it the model just imagines what the tool would have said.

EXAMPLE 1Making the model check instead of guess
SituationSame job as above — is old_price_calc safe to delete? You have given the model a search_code tool.
We wantIt to use the tool. Every time. Not just when it feels unsure.
Why it is hardHaving a tool available is not the same as being told to use it. A model that can check will often answer from a guess instead, because guessing is faster and it does not know it is guessing.
✗Wrong approach
You are a helpful coding assistant.

"You have access to" is an offer, not an instruction. The model treats the tools as optional and answers from its own guess whenever the question sounds familiar — which is most of the time.
✓Right approach

· NEVER say anything about a file, a
  function or a line number unless you
  read it with a tool in this session.
· If no tool can tell you something,
  say "I could not check X" — do not
  guess and do not estimate.

Written as a ban, not a suggestion. "Use the tools when helpful" gets ignored. "Never state a fact you did not read" does not.

ReAct — Two More Examples

The two things that will actually break your agent in week two: an error that disappears, and a loop that never ends. Then where to use it, and a summary.

EXAMPLE 3An error that turns into a fact
SituationYour agent looks up a customer's orders. The database is slow today and the call times out.
We wantThe agent to say "I could not check" — not to decide the customer has no orders.
Why it is hardThere is a huge difference between "the lookup failed" and "the lookup worked and found nothing". If your code hides that difference, the model cannot tell them apart either.
✗Wrong approach
try:
    result = run_tool(name, args)
except Exception:
    result = ""
What the agent then says
I checked and this customer has no orders on file.
The model got an empty string and read it as "nothing found". A crash has quietly become a fact. This is the most common way an agent gives a confidently wrong answer, and nothing in your logs looks unusual.
✓Right approach
except TimeoutError:
    result = ("ERROR: the database did
      not answer within 5 seconds. Try
      once more. If it fails again, tell
      the user you could not check.")

except NotFound:
    result = ("EMPTY: the search worked
      and there are no matching orders.
      This is a real answer. Do not
      search again.")
What the agent then says
I tried twice but the order system did not respond. I could not check this customer's orders — please try again in a few minutes.
Two different messages for two different situations, and each one says what to do next. Errors are information the model needs, not something to hide.
Lesson
Never swallow an error. Pass it back to the model as plain text that explains what happened and what to try next. And always separate "it broke" from "it worked and the answer is nothing".
EXAMPLE 4The agent that runs forever
SituationYour agent searches for an order by email. The email has a typo, so the search correctly returns nothing. The agent reads "nothing" as failure and tries again.
We wantIt to stop after a couple of tries and say what it could and could not find.
Why it is hardNothing crashes. The agent looks busy. It is simply doing the same useless thing over and over, and it will keep doing it until something outside stops it.
✗Wrong approach
while True:
    reply = ask(messages, tools=tools)
    ...
What happens
search_orders(email="a@b.com") → [] search_orders(email="a@b.com") → [] search_orders(email="a@b.com") → [] ... 1,400 times
No limit on rounds, no limit on time, no limit on money, and nothing that notices the agent is repeating itself. This is the number one way student projects burn through an API budget overnight.
✓Right approach
seen = set()
for step in range(8):                   # limit 1: rounds
    if seconds_used() > 60: break       # limit 2: time
    if money_spent() > 0.25: break      # limit 3: cost

    call = ask(messages, tools=tools)

    key = (call.name, str(call.args))   # limit 4: repeats
    if key in seen:
        result = ("ERROR: you already made this
          exact call. Change the arguments, use
          a different tool, or answer with what
          you have and say what is missing.")
    else:
        seen.add(key)
        result = run_tool(call)

    log(step, call, result)             # always log

return {"answer": ..., "found": facts,
        "could_not_check": gaps}
Four limits and a log. "I found the customer but could not check their orders" is a useful answer. Silence after ninety seconds is not.
Lesson
Every agent needs four brakes — rounds, time, money, and a check for repeated calls — plus a log of every step. Without the log, a wrong answer three weeks later is impossible to explain.

SKILL.md — Your Procedures In Files

The four techniques so far decide how the model thinks. None of them tell it how your team reviews code, or writes release notes, or closes the month. That knowledge goes in files the agent opens only when it needs them.

What problem does it solve?

Say your team has forty written procedures. Code review, pull request descriptions, release notes, the on-call runbook, the SQL naming rules, the migration checklist. Each one is one or two pages.

You could paste all forty into the system prompt. Here is what that costs:

All forty in the prompt
the obvious way
  • About 60,000 words of instructions sent with every message — including "what time is standup?"
  • You pay for all of it on every single request
  • Thirty-nine irrelevant procedures competing for attention with the one that matters
  • Changing one line means editing a giant file and re-testing everything
Forty small files
the SKILL.md way
  • Only the name and one-line description of each is loaded — about 25 words each, 1,000 in total
  • The full procedure is opened only when the description matches what you asked for
  • Extra reference files are read only at the step that needs them
  • Each file is small, reviewed on its own, and kept in git like any other code

How it works — three levels

Level 1 · always loaded
The name and description
About 25 words per skill. This is all the agent knows about a skill until it decides to use it. Like reading the contents page of a manual.
Level 2 · loaded when needed
The procedure itself
The steps. A page or two. Loaded only when your request matches the description. Like opening to the right chapter.
Level 3 · read at the step
Extra files and scripts
Checklists, style guides, scripts. Read only if step 4 actually says to read them. These can be huge and cost nothing until used.
A way to remember it

Think of a car repair manual. You do not read all 900 pages before touching the car. You look at the contents page, open the one chapter you need, and follow the link in step 4 only if step 4 comes up. That is exactly what a skill does.

What a skill looks like on disk

a folder, with one required file

└── code-review/
    ├── SKILL.md              # the description + the steps
    ├── checklist.md          # level 3 - read only at step 3
    └── scripts/
        └── changed_files.sh  # run, not read - costs nothing
code-review/SKILL.md
---
name: code-review
description: Review a pull request or a set of changes for bugs,
  security problems and broken conventions. Use when asked to review
  code, check a PR, look over a change, or check something before
  merge. Not for writing new code.
allowed-tools: Read, Grep, Bash(git diff:*)
---

# Code review

## Step 1 - get the list of changed files
Run `scripts/changed_files.sh`.
If it lists more than 40 files, stop and ask which part to review.
Read only the files that changed. Never read the whole project.

## Step 2 - three passes, in this order
1. Bugs - off-by-one, missing null checks, unhandled errors.
2. Security - check permissions on every new endpoint, look for
   passwords or keys in the code, look for user input in queries.
3. Conventions - read `checklist.md` now and apply it.

## Step 3 - check each finding before you report it
For every problem you found, write the exact input that triggers it.
If you cannot write that input, DELETE the finding.
Findings you cannot demonstrate are noise, and noise is why people
stop reading reviews.

## Step 4 - output
A markdown table: file and line, how serious, one line describing it,
the input that breaks it, and the suggested fix.
Worst first. Maximum 10 rows.
If you found nothing, write exactly "No blocking findings." and stop.

## Do not
- Do not comment on formatting. The formatter handles that.
- Do not suggest renaming things unless the name is actually wrong.
- Do not include praise or a summary paragraph.

Now read that again as a prompt, not as a document. Everything from this deck is in it. The numbered steps are Chain of Thought. "Three passes, in this order" breaks the job into pieces. "Write the input or delete the finding" is a check before reporting. The allowed-tools line means this skill can read but never write. And checklist.md stays out of the file so the procedure is short enough to actually follow.

Three parts: what it does, the words people will actually say, and what it is not for. The last part is what stops it firing on "write me a login function".
Lesson
Write the description for the model that has to choose, not for a human reading a list. Then test it: write five sentences your team would really say, and check all five trigger it.
EXAMPLE 2A skill that reads like an essay
SituationYour skill fires correctly, but every review it produces is different, and it keeps missing the security checks.
We wantThe same checks, in the same order, every time — so two reviews of the same PR look the same.
Why it is hardAdvice is not instructions. "Be thorough" cannot be followed and cannot be checked.
✗Wrong approach
# Code review

Good code review is about being helpful
as well as correct. Try to be thorough
but also kind. Think about the wider
design, and remember the author may
know things you do not.
All of this is true and none of it can be done. There is no step to carry out, nothing to tick off, and no way to tell whether the skill was followed. It is a blog post, and the agent reads it before every review.
✓Right approach
# Code review

## Step 1 - get the changed files
Run `git diff main...HEAD --stat`.
More than 40 files? Stop and ask.

## Step 2 - bugs
Check every loop boundary and every
value that could be null.

## Step 3 - security
Permissions on each new endpoint.
Any password or key in the code.
Any user input going into a query.

## Step 4 - report
Max 10 findings, worst first.
Nothing found? Write "No blocking
findings." and stop.
Numbered, in order, and every step is something you can confirm happened. A skill is a procedure, not an explanation. If a line cannot be carried out, it does not belong in the file.
Lesson
Write it the way you would write instructions for a new team member on their first day. Numbered steps. Concrete checks. A clear stopping point.

SKILL.md — Two More Examples

One about keeping the file small, one about not asking the model to do a job a script can do. Then how skills relate to AGENTS.md, where to use them, and a summary.

EXAMPLE 3Putting everything in one file
SituationYour team has a 2,000-line style guide. Step 4 of your review skill needs it. So you pasted the whole thing into SKILL.md.
We wantThe style rules applied — without paying for 2,000 lines on every review, most of which will be about a language the PR does not even use.
Why it is hardIt feels safer to put everything in one place. But the whole point of level 3 is that depth is free as long as it stays behind a pointer.
✗Wrong approach
# SKILL.md - 2,800 lines

## Step 4 - apply the style guide

[the entire 2,000-line style guide,
 pasted in, loaded in full every
 single time this skill runs]
A Python-only pull request now loads all the TypeScript, CSS and SQL rules too. The steps that matter are buried in the middle, and the model has 2,000 lines of mostly irrelevant text to work through before it starts.
✓Right approach
# SKILL.md - about 60 lines

## Step 4 - apply the style guide
Read `references/style-guide.md` now.
Read only the section for the language
of the changed files:
  Python     - section 3
  TypeScript - section 5
  SQL        - section 8
Do not read the other sections.
The guide stays in the folder, as big as you like. The skill says when to open it and which part to read. A Python PR now loads one section instead of eight.
Lesson
Keep the steps short. Put the long reference material in separate files and point at them from the step that needs them. A file the agent might read costs nothing until it reads it.
EXAMPLE 4Asking the model to do a script's job
SituationStep 1 of your skill needs the ten largest files in the project, with their line counts.
We wantThe correct ten files, quickly, and the same ten every time.
Why it is hardA model asked to count things will produce numbers that look right. You will not notice when they are not.
✗Wrong approach
## Step 1
Read every file in src/, count the
lines in each one, and list the ten
largest.
Slow, expensive, and the answer changes between runs. It also fills the agent's memory with source code it does not need, leaving less room for the actual review. And if it miscounts, nothing tells you.
✓Right approach
## Step 1
Run `scripts/largest.sh`.
It prints the ten largest files with
their line counts.
Use its output. Do not read src/
yourself.

# scripts/largest.sh
wc -l src/**/*.py | sort -rn | head -10
Exact, instant, free, and identical every time. Anything a script can do, a script should do. The model's job is judgement, not counting.
Lesson
Before you write a step, ask: could five lines of shell do this? If yes, write the shell, and make the step say "run this script and use the output".

One sentence to keep them straight

AGENTS.md is what is always true here. A skill is what to do when a certain kind of job comes in. An MCP server is what the agent can reach. A slash command is you saying "do this specific thing, now." Putting a procedure in AGENTS.md makes every task pay for it. Putting always-true project facts in a skill means they only load sometimes, which is worse.

Summary — SKILL.md
Four things to take away
  1. What it is: your procedure in a file. Only the one-line description is always loaded; the steps load when the job comes in.
  2. The description does the choosing. Put the words people actually say in it, and say what the skill is not for.
  3. The body is a procedure, not an essay. Numbered steps, a stopping point, a check, and an exact output shape.
  4. Keep it short and point at the rest. Big reference files and scripts sit beside it and cost nothing until a step opens them.
You wrote a code review skill. Two weeks later nobody can get it to run. What do you fix first?
The steps are invisible until the skill fires. When the model is choosing, it has seen exactly one line about your skill. If that line says "a skill for reviewing code" and your team says "sanity-check this diff for me", there is nothing to match on. Rewrite the description, then test it with five real sentences.

One job, all five together

Your manager asks: "Our checkout page has been getting slower for three months. Find out why and tell me what to do about it."

1
SKILL.md gives the procedure
Your request matches the performance-investigation skill. Its steps say which dashboards to check, which log queries to run, and that any claim about a slowdown must come with a number and a date.
2
ReAct gathers the facts
Read the response-time chart. Read the deploy history for those three months. Query the slow-query log. Read the checkout code. Every number now comes from something the agent actually looked at. Capped at 30 steps.
3
Graph of Thought puts the picture together
Findings from four sources joined in pairs. The deploy log says nothing changed on 14 June; the response-time chart says something clearly did. That disagreement is kept and flagged, and it turns out to be the clue — a config change, not a deploy.
4
Tree of Thought works out what to do
Three genuinely different fixes: add an index, cache the result, or change the query. Each scored on how much it would help, how long it would take, and how easily it could be undone. Two are explored further, one is chosen — and all three are reported with their scores.
5
Chain of Thought does the sums
Inside the chosen fix: how many rows the index would cover, how much disk it needs, the expected drop in response time. One line per calculation, the total at the end.
6
The improve loop finishes it
A critic checks the report against the skill's checklist. Maximum three rounds. It returns the best version it saw, not the last one.
The point of this example

Nobody picked "a technique" for this job. Each one does the single thing it is good at, at the moment that thing is needed. That is how real systems are built — not by choosing one technique and using it everywhere.

Two sums to do before you build anything

1 · What does a wrong answer cost? A wrongly labelled support ticket costs a minute of someone's time. A wrong database choice costs a quarter. Spend in proportion.

2 · What does the human version cost? Ninety model calls is nothing compared to two days of an analyst's time — and a waste compared to thirty seconds of asking a colleague. Most bad decisions in this area come from never doing this second sum.

Three mistakes that apply to all five

✗
Jumping to the most impressive techniqueThe most common mistake by far. One well-written single call solves more real problems than everything on this slide put together.
✗
Never measuring anythingIf you cannot say "the simple version got 71% and this gets 84%", you are choosing by feel. Build a set of 20 test cases before you build anything else.
✗
No limits anywhereTrees, improve loops and agents all run forever by default. Cap the rounds, the time and the money — and always return whatever you got.
✗
Thinking harder about a missing factNone of these can invent information the model never had. If the answer is in a file, go and read the file.

Which One Should I Use?

Five questions, asked in this order. Then a table of real jobs, a checklist, and the five sentences worth remembering.

Ask these five, in this order

1
Does the answer depend on something the model cannot know?
Your code, your database, today's date, your company's rules. Yes → ReAct. Nothing else helps. Thinking harder about a fact you do not have just gives you a longer invention.
2
Does the answer need more than two steps of working?
Sums, applying rules, tracing a bug. Yes → Chain of Thought. Write out the steps yourself and put the answer last. This costs almost nothing and helps the most.
3
Could two good engineers disagree about the best answer?
Design decisions, planning, naming. Yes, and you can score an option → Tree of Thought. If you cannot write the scoring rules, do not build the tree — run the prompt five times and vote instead.
4
Is the answer built out of many pieces that must all survive?
Ten documents, four review passes, several teams' requirements. Yes → Graph of Thought. Join lists with rules, and keep every disagreement.
5
Will this same job come back next week?
And is it specific to how your team works? Yes → write it as a SKILL.md. Whatever mix of the four you ended up with, that is now a procedure, and procedures belong in files.
And one question before all five

Have you tried just asking, properly, and written down how well it did? About half the problems people bring to Tree of Thought are solved by a prompt with named steps, a clear output format, and the answer moved to the end. You need that number anyway — it is what everything else gets compared against.

The five sentences worth remembering
If you forget everything else
  1. The words the model writes are its rough paper. No space for the working means there was no working — so always put the answer last.
  2. A tree is only as good as its scoring. Say what 0 and 1 mean, or better, use a real check like a test run.
  3. Join lists, never paragraphs. Every join over prose loses detail, and you are about to do it several more times.
  4. No amount of thinking creates a missing fact. If the answer is in a file or a database, the model has to go and read it.
  5. Start simple, measure, and only add complexity when the number tells you to. The usual failure is not a weak prompt — it is a clever system built on a baseline nobody ever measured.
