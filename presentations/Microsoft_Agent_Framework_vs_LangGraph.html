01

The API entry point

A customer request invokes the graph or workflow

LangGraph

# Illustrative API adapter; app is already compiled.
# Request body: {"message": "My account is locked..."}
def handle_ticket(payload: dict) -> dict:
    return app.invoke({"ticket": payload["message"]})

Microsoft Agent Framework

# Illustrative API adapter; functions are already defined.
# Build an isolated workflow before executing this request.
async def handle_ticket(payload: dict) -> dict:
    workflow = create_workflow()
    run = await workflow.run(payload["message"])
    return run.get_outputs()[0]

These adapters are illustrative Python functions, not a deployed HTTP service. A web framework would map a request body to payload and serialize the returned dictionary. They invoke the orchestrator; they do not call the LLM directly.

{
  "message": "My account is locked and I have an important meeting in 10 minutes."
}

Response fields: ticket, analysis (summary/category/urgency), decision, reply. We will trace those exact fields through the implementation.

02

Teaching order and runtime order

We reveal the internals after seeing the entry point

Define steps → Build / compile → Invoke → Execute steps → Return output

That is the actual lifecycle. This presentation first shows an already-prepared handler, then opens the implementation one part at a time. Compilation does not occur after the agents finish.

At build timeAt request time
LangGraph: define nodes/state, add edges, call compile().Call app.invoke(...); the runtime schedules nodes.
Microsoft: define step functions; create_workflow() wraps fresh executors and calls build().The handler builds an isolated instance before workflow.run(...); the runtime schedules executors.

A graph invocation starts the whole process. A model call happens later inside analysis, decision, or reply. The four steps are not four autonomous agents.

The eventual ticket state schema

Eventual state fields; only the ticket input is supplied at the start

LangGraph

from typing import TypedDict, Optional

class TicketState(TypedDict):
    ticket: str
    analysis: Optional[dict]
    decision: Optional[str]
    reply: Optional[str]

Microsoft Agent Framework

from typing import TypedDict, Optional

class TicketState(TypedDict):
    ticket: str
    analysis: Optional[dict]
    decision: Optional[str]
    reply: Optional[str]
FieldWritten byExpected value
ticketclean stepCleaned customer message
analysis.summary / category / urgencyanalysis stepThree model text responses
decisiondecision stepYes/No plus a reason, as free text
replyreply stepCustomer-facing free text

Both implementations use the same executable TicketState declaration and the same eventual fields. This describes application types, not supplied initial values. Both start with only the ticket input; analysis, decision, and reply are written by their steps.

Optional allows None in the annotation but does not populate a default. Microsoft uses TicketState for the final result and runner return annotations. Native state is accessed with WorkflowContext.get_state() and set_state().

LangGraph passes the schema to StateGraph(TicketState); Microsoft connects executors with WorkflowBuilder and does not register this TypedDict as a schema argument. The same declaration does not imply identical update, reducer, or runtime-validation semantics.

06

One model agent, four workflow steps

Model calls and orchestrator calls have different jobs

StepModel callsResponsibility
clean_step0Trim and validate input
analyse_ticket3Summary, category, urgency
add_decision1Recommend escalation
add_reply1Write the reply

Microsoft reuses one configured TicketSupport Agent without a shared AgentSession. LangGraph calls a configured ChatOpenAI wrapper inside its Python nodes. The workflow order is fixed by the application; neither model chooses the next step.

In Microsoft, every executor reads and writes native workflow state. The string "continue" is a routing trigger only. In LangGraph, nodes return state updates and graph edges select the next node.

07

Step 1 · Clean input

Return a state update versus write native shared state

Reads: Raw customer input. Writes: ticket. This is the actual companion notebook implementation.

LangGraph

def clean_node(state: TicketState) -> dict:
    message = state["ticket"].strip()

    if not message:
        raise ValueError("Ticket cannot be empty.")

    return {"ticket": message}

Microsoft Agent Framework

async def clean_step(message: str, ctx: WorkflowContext[str]) -> None:
    ticket = message.strip()
    if not ticket:
        raise ValueError("Ticket cannot be empty.")
    ctx.set_state("ticket", ticket)
    await ctx.send_message("continue")

Both strip whitespace and reject empty tickets before any model call. LangGraph applies the returned update; Microsoft writes the ticket with ctx.set_state. The "continue" message activates the next executor and carries no ticket data.

Step 2 · Analyse the ticket

Three identical prompts, executed sequentially

Reads: ticket. Writes: analysis. This is the actual companion notebook implementation.

LangGraph

def analyse_node(state: TicketState) -> dict:
    ticket = state["ticket"]

    summary = model.invoke(
        f"Summarize this support ticket in one short sentence:\n{ticket}"
    ).content.strip()

    category = model.invoke(
        f"Return only one category: billing, technical, or account.\nTicket: {ticket}"
    ).content.strip()

    urgency = model.invoke(
        f"Return only one urgency: low, medium, or high.\nTicket: {ticket}"
    ).content.strip()

    return {
        "analysis": {
            "summary": summary,
            "category": category,
            "urgency": urgency,
        }
    }

Microsoft Agent Framework

async def analyse_ticket(trigger: str, ctx: WorkflowContext[str]) -> None:
    ticket = ctx.get_state("ticket")

    summary = (await agent.run(
        f"Summarize this support ticket in one short sentence:\n{ticket}"
    )).text.strip()

    category = (await agent.run(
        f"Return only one category: billing, technical, or account.\nTicket: {ticket}"
    )).text.strip()

    urgency = (await agent.run(
        f"Return only one urgency: low, medium, or high.\nTicket: {ticket}"
    )).text.strip()

    analysis: dict = {
        "summary": summary,
        "category": category,
        "urgency": urgency,
    }
    ctx.set_state("analysis", analysis)
    await ctx.send_message("continue")

In both implementations, summary, category, and urgency run in order. The LCEL notebook runs them concurrently with RunnableParallel. Async functions alone do not create parallel analysis.

Step 4 · Write the reply

The same customer-facing prompt, different output mechanism

Reads: ticket, decision. Writes: reply. This is the actual companion notebook implementation.

LangGraph

def reply_node(state: TicketState) -> dict:
    prompt = f"""
You are a customer-support assistant.

Customer message:
{state['ticket']}

Decision:
{state['decision']}

Write a short and helpful reply to the customer.
Do not mention prompts, AI, or internal system details.
"""

    reply = model.invoke(prompt).content.strip()

    return {"reply": reply}

Microsoft Agent Framework

async def add_reply(trigger: str, ctx: WorkflowContext[Never, dict]) -> None:
    ticket = ctx.get_state("ticket")
    decision = ctx.get_state("decision")
    prompt = f"""
You are a customer-support assistant.

Customer message:
{ticket}

Decision:
{decision}

Write a short and helpful reply to the customer.
Do not mention prompts, AI, or internal system details.
"""

    reply = (await agent.run(prompt)).text.strip()

    ctx.set_state("reply", reply)
    result: TicketState = {
        "ticket": ctx.get_state("ticket"),
        "analysis": ctx.get_state("analysis"),
        "decision": ctx.get_state("decision"),
        "reply": ctx.get_state("reply"),
    }
    await ctx.yield_output(result)

Microsoft stores the reply in native state, then yields a snapshot of all four fields. send_message("continue") activates another executor; yield_output exposes the final result to the caller. The final executor declares WorkflowContext[Never, dict].

16

Connect and run

The edges encode the same linear process

LangGraph

from langgraph.graph import StateGraph, START, END

builder = StateGraph(TicketState)
builder.add_node("clean_step", clean_node)
builder.add_node("analyse_ticket", analyse_node)
builder.add_node("add_decision", decision_node)
builder.add_node("add_reply", reply_node)
builder.add_edge(START, "clean_step")
builder.add_edge("clean_step", "analyse_ticket")
builder.add_edge("analyse_ticket", "add_decision")
builder.add_edge("add_decision", "add_reply")
builder.add_edge("add_reply", END)
app = builder.compile()
result = app.invoke({"ticket": message})

Microsoft Agent Framework

def create_workflow():
    clean = executor(id="clean_step")(clean_step)
    analyse = executor(id="analyse_ticket")(analyse_ticket)
    decide = executor(id="add_decision")(add_decision)
    reply = executor(id="add_reply")(add_reply)
    return (
        WorkflowBuilder(start_executor=clean, output_from=[reply])
        .add_edge(clean, analyse)
        .add_edge(analyse, decide)
        .add_edge(decide, reply)
        .build()
    )

workflow = create_workflow()
run_result = await workflow.run(message)
result = run_result.get_outputs()[0]

Microsoft gets fresh executor instances and a fresh workflow with isolated native state per ticket. The factory wraps each function with executor(id=...)(function), equivalent to decorator syntax. In Jupyter use await solve_ticket(message); its event loop is already running. The code above is an orchestration excerpt; full runnable setup is in the companion notebooks.

Three different things, with different lifetimes

Workflow stateCurrent ticket fields used by stepsEnabled in both; native shared state
CheckpointSaved execution state plus progress information for replay/recoveryNot configured in either notebook
Agent chat historyMessages supplied to later model turnsNo Microsoft AgentSession is passed; LangGraph state has no messages field

The next slides are an optional extension. The current notebooks run from clean to reply without saving checkpoints or pausing. The extension reuses the same nodes/executors and uses fixed responses to avoid paid calls.

Saving the ticket dictionary alone does not tell a runtime which step should run next. A checkpoint also preserves scheduling/progress information. Restoring workflow state does not automatically give the model conversational memory.

Validation used the actual runtimes: five fixture model calls on the first run, two more after restoring the analysis checkpoint, and the same final dictionary in both frameworks. Restoring an earlier point re-executes later work; a live replay can produce different text and additional API cost.

What Microsoft Agent Framework provides

Agents and explicit workflows in one framework

  • Agent: wraps a model client, instructions, optional tools, and optional conversation session.
  • Workflow: controls an explicit path through functions or agents.
  • Executor: one unit of work; shared state stores ticket data, and edges route messages that activate the next executor.
  • Python and .NET support can matter when your organisation builds services in both languages.

It succeeds the AutoGen and Semantic Kernel line of work. This lesson uses current agent_framework APIs, not autogen.

Official overview

What LangGraph provides

A runtime for explicit, stateful graph execution

LangGraph centres the graph and its shared state. Nodes read state and return updates. Edges control the next step. You can mix ordinary code and model calls.

  • Useful when state transitions, loops, branching, and resumable workflows are the main design problem.
  • Persistence and human review require the appropriate runtime configuration; a simple graph is not automatically durable.
  • LangChain components are optional; this project happens to use ChatOpenAI.

Both support shared state and can orchestrate agents. Microsoft state writes do not schedule executors: edges still deliver a minimal control message. Its pinned runtime stages key writes at superstep boundaries; this is not LangGraph reducer behaviour. Both need deliberate persistence, error handling, and observability setup for a production service. Those capabilities are outside this small lesson.

Concrete reasons to choose Microsoft

Choose it when these needs match your team

  • Python + .NET organisation: use the same framework family and shared agent/workflow vocabulary across services; APIs still differ by language.
  • Agent abstraction is central: model clients, tools, sessions, and middleware live alongside workflow orchestration.
  • Existing Microsoft agent investment: evaluate it when modernising AutoGen / Semantic Kernel or integrating with Foundry.
  • Reusable agent coordination: its built-in sequential, concurrent, handoff, and group-chat patterns may reduce custom orchestration.

These are selection criteria, not proof of higher accuracy, lower cost, or faster execution. The ticket demo itself needs none of those integrations.

27

When LangGraph fits better

Keep the graph and state as the main abstraction

  • Your Python team already understands and operates LangGraph successfully.
  • You need detailed control of custom state transitions, loops, and human review points.
  • Your existing LangChain integrations and LangSmith workflow are useful to the team.
  • The current system meets requirements: changing frameworks would create work without a demonstrated benefit.

LangGraph can use Azure models too. Microsoft Agent Framework can use non-Microsoft providers. Azure usage alone does not require migration.

Should this ticket solver migrate?

For this small pipeline, migration is a learning choice

No operational requirement here forces migration. All four notebooks solve the same small problem. Pure Python may already be sufficient.

  • Name one unmet need: shared .NET framework, agent integration, checkpoint behaviour, or reusable coordination.
  • Port the same prompts and compare output contract, failures, latency, and cost with a representative ticket set.
  • Check persistence, session isolation, tool behaviour, and monitoring before replacing a running system.
  • Keep the working implementation until the replacement meets measurable requirements.

The new notebook demonstrates a different programming model; it does not claim a quality or performance improvement.

29

Classroom check

Predict what the code actually does

Does async make the three analyses run together?

No. Each await finishes before the next call starts. Concurrent execution needs an explicit concurrency design.

Is an executor a tool the LLM decides to call?

No. Workflow edges schedule these executors. There are no model-selected tools in this project.

Where is conversation memory enabled?

Nowhere in these examples. Microsoft calls omit a shared AgentSession, and LangGraph has no checkpointer configured.

Will the same framework guarantee a better reply?

No. Model, prompts, context, tools, and evaluation matter. Orchestration alone does not establish better answer quality.
