These are illustrative Python API adapters, not deployed HTTP endpoints. An actual server would validate its request body and serialize the returned dictionary. The notebook itself supplies the workflow.

Actual lifecycle: define agents and stages, build/compile the workflow, then run the request. The teaching slides reveal those definitions after the consumer entry point. Build never happens after the agents finish.

Graph invocation runs the complete team. The ask helper inside a stage performs an individual model/agent call.

Microsoft Agent Framework

def read_travel_state(ctx: WorkflowContext) -> TravelState:
    """Read a local snapshot from native workflow state, preserving absent keys."""
    missing = object()
    snapshot = {}
    for key in TravelState.__annotations__:
        value = ctx.get_state(key, missing)
        if value is not missing:
            snapshot[key] = value
    return cast(TravelState, snapshot)

def write_travel_update(ctx, update: dict) -> None:
    """Apply only changed fields. This is explicit assignment, not a reducer."""
    for key, value in update.items():
        ctx.set_state(key, value)

LangGraph applies returned updates to graph state. Microsoft explicitly reads and writes its framework-owned store. read_travel_state makes a local copy for unchanged stage functions. It does not forward state to another executor or replace the native store.

Manager stage

LangGraph

def manager_node(state):
    """Read the request. Write down the requirements. Decide who should work."""
    requirements = ask(manager_agent, f"""
Read this travel request and list what you understood.

REQUEST: {state['request']}

List these lines only:
FROM, TO, DAYS, TRAVELLERS, BUDGET, INTERESTS, HARD RULES, MISSING INFO
""")

    choice = ask(manager_agent, f"""
Here are the requirements:
{requirements}

Which specialists are needed? Choose from: flight_agent, hotel_agent, activity_agent.
Reply with the names separated by commas and nothing else.
""")

    # Keep only names we actually have. This protects us if the model adds something extra.
    valid = ["flight_agent", "hotel_agent", "activity_agent"]
    workers = [name for name in valid if name in choice.lower()]
    if not workers:
        workers = valid          # if unsure, use everyone

    print("MANAGER understood the request.")
    print("MANAGER picked:", ", ".join(workers))
    return {"requirements": requirements, "chosen_workers": workers}

@executor(id="selected_workers")
async def workers_step(signal: str, ctx: WorkflowContext[str]) -> None:

LangGraph has separate flight, hotel and activity vertices. Microsoft combines their concurrent tasks and collector barrier inside selected_workers. The same business flow therefore has seven LangGraph nodes and five Microsoft executors.

Graph and workflow construction

The code expresses the same business-stage order

LangGraph

from langgraph.graph import StateGraph, START, END

graph = StateGraph(TravelState)

# Add every step
graph.add_node("manager", manager_node)
graph.add_node("flight_agent", flight_node)
graph.add_node("hotel_agent", hotel_node)
graph.add_node("activity_agent", activity_node)
graph.add_node("synthesis", synthesis_node)
graph.add_node("critic", critic_node)
graph.add_node("revision", revision_node)

# Start at the manager
graph.add_edge(START, "manager")

# The manager's list of workers decides who runs. All of them start together.
graph.add_conditional_edges(
    "manager",
    lambda state: state["chosen_workers"],
    ["flight_agent", "hotel_agent", "activity_agent"],
)

# Whoever ran, they all meet at synthesis
graph.add_edge("flight_agent", "synthesis")
graph.add_edge("hotel_agent", "synthesis")
graph.add_edge("activity_agent", "synthesis")

# Then the quality loop
graph.add_edge("synthesis", "critic")
graph.add_edge("critic", "revision")
graph.add_edge("revision", END)

travel_planner = graph.compile()
print("Graph built.")

Microsoft Agent Framework

def create_workflow():
    return (WorkflowBuilder(start_executor=manager_step, output_from=[revision_step])
        .add_edge(manager_step, workers_step)
        .add_edge(workers_step, synthesis_step)
        .add_edge(synthesis_step, critic_step)
        .add_edge(critic_step, revision_step).build())

The Microsoft graph has five executors. Three business workers live inside the selected-workers executor. Edges carry “continue”. Both notebooks omit checkpoint configuration in their normal build functions.

async def run_travel_state(request: str) -> TravelState:
    # Fresh workflow => fresh framework-owned shared state for this request.
    run_result = await create_workflow().run(request)
    outputs = run_result.get_outputs()
    if len(outputs) != 1:
        raise RuntimeError(f"Expected one final state, got {len(outputs)}")
    return cast(TravelState, outputs[0])

Three different objects with different lifetimes

ObjectWhat it containsCurrent notebooks
Workflow stateBusiness request, requirements, reports, draft, critique, final planBoth frameworks use it during execution.
Persisted checkpointWorkflow state plus runtime progress required to continueNeither normal notebook build enables it.

Saving workflow fields does not automatically save an agent’s complete chat transcript. Reports are model outputs stored in workflow state, not a replacement for the internal tool conversation.

LangGraph checkpoint and resume

Optional pause before synthesis, then continue the same thread

from langgraph.checkpoint.memory import InMemorySaver

# OPTIONAL EXTENSION: original notebook compiles without a checkpointer.
checkpointer = InMemorySaver()
checkpoint_app = graph.compile(
    checkpointer=checkpointer,
    interrupt_before=["synthesis"],
)
config = {"configurable": {"thread_id": "travel-demo-1"}}

# Pause after all selected workers finish, before synthesis.
checkpoint_app.invoke({"request": demo_request}, config)
saved = checkpoint_app.get_state(config)
assert saved.next == ("synthesis",)
assert "activity_report" in saved.values
assert "draft_plan" not in saved.values

# Resume the paused thread without supplying a new request.
final_state = checkpoint_app.invoke(None, config)
print(final_state["final_plan"])

The checkpoint includes the request, requirements, chosen_workers and selected reports. saved.next identifies synthesis as pending. invoke(None, config) resumes the paused thread instead of sending a new request. The test confirmed that manager and workers did not run again.

Microsoft checkpoint replay

Optional replay from an earlier recorded barrier

from agent_framework import InMemoryCheckpointStorage, WorkflowBuilder

# OPTIONAL EXTENSION: current notebook does not enable checkpoint storage.
checkpoint_storage = InMemoryCheckpointStorage()

def create_checkpoint_workflow():
    return (WorkflowBuilder(
        name="travel-checkpoint-demo",
        start_executor=manager_step,
        output_from=[revision_step],
        checkpoint_storage=checkpoint_storage,
    ).add_edge(manager_step, workers_step)
     .add_edge(workers_step, synthesis_step)
     .add_edge(synthesis_step, critic_step)
     .add_edge(critic_step, revision_step).build())

# Optional live extension with notebook definitions loaded.
# Developer tests intercept HTTP externally; notebook has no offline mode.
recording = create_checkpoint_workflow()
recorded = await recording.run(demo_request)
checkpoints = await checkpoint_storage.list_checkpoints(
    workflow_name="travel-checkpoint-demo")
worker_checkpoint = next(cp for cp in checkpoints
    if "activity_report" in cp.state and "draft_plan" not in cp.state)

# Replay from the recorded barrier, using the same graph and storage.
# This is a completed-run replay, not an intentional pause mechanism.
restored = create_checkpoint_workflow()
resumed = await restored.run(checkpoint_id=str(worker_checkpoint.checkpoint_id))
final_state = resumed.get_outputs()[0]
assert final_state == recorded.get_outputs()[0]

This example first completes a recording run, selects the saved worker boundary, then replays downstream stages from it. It demonstrates restore, not an intentional pause API. Same graph structure and storage are required. External tests with intercepted provider HTTP confirmed that only synthesis, critic and revision ran on replay.

34

Checkpoint limits

Saved progress does not guarantee exactly-once effects

  • The examples use in-memory storage. A persistent backend and a stable graph/version strategy are separate deployment decisions. Colab runtime deletion loses these examples’ checkpoints.
  • Restoring an earlier checkpoint can rerun downstream calls and side effects. Replayed live model calls can cost money and return different wording. The separate validation script uses deterministic intercepted responses to check equality without paid calls.
  • No checkpoint is enabled by default. No hosted Colab restart, external database durability or process-crash recovery test is claimed.
  • Workflow state snapshots do not contain API keys in this project. Agent clients, model availability and credentials must be configured again in a new process.

Choose a new LangGraph thread_id for a new trip. Microsoft’s normal wrapper creates a fresh workflow for a new trip. Use the matching persisted identity only when you intend to continue or replay that execution.
