02

Code quality: linting and formatting

A linter finds code mistakes. A formatter keeps code style consistent.

Why we need itSmall mistakes become harder to spot as the app grows.

When to add itNow. Run the checks before each pull request.

Travel Planner example
Proposed tools: ESLint + Prettier for the Vite frontend. Ruff for the FastAPI backend. Formatting alone cannot prove that trip planning works.

Today: Vite + FastAPI + LangGraph + local RAG. Saved chats, login and editable trips are proposed work. This deck is a path to production.

03

Git branches, reviews and pull requests

A branch holds a change. A pull request asks the team to review it.

Why we need itA review can catch wrong assumptions before they reach users.

When to add itFor each change, starting with the next feature.

Travel Planner example
Example: codex/saved-chats. Ask the coding agent to add chat saving only. Accept it when chats survive refresh and another user cannot read them.

04

Database selection for saved data

A database stores app data after a page refresh or server restart.

Why we need itMy Trips and saved conversations need durable records.

When to add itBefore adding chat history, follow-ups or My Trips.

Travel Planner example
Proposed default: PostgreSQL for linked records and transactions. MongoDB is an alternative for flexible document records. Keep ChromaDB for now. Vector search does not replace chat storage.

Follow-ups also need the backend to load the selected chat and pass useful history into planning. Saving messages alone does not create memory.

05

Data models, ORM and migrations

A model defines stored fields. An ORM maps code to SQL tables.

Why we need itClear links keep each message and itinerary attached to its owner.

When to add itDesign these before writing the save and edit APIs.

Travel Planner example
Proposed Python stack: SQLAlchemy + Alembic. MongoDB uses document models and may use an ODM. Add a trip version field so two edits can detect a conflict. Back up data before risky migrations.

06

Authentication and authorization

Authentication checks who you are. Authorization checks what you may do.

Why we need itA logged-in user must see only their own chats and trips.

When to add itBefore allowing multiple people to use saved data.

Travel Planner example
Use a trusted sign-in library or service. The backend checks ownership on every read, edit and delete. A user_id sent by the browser is not proof of identity.

07

API design and external APIs

An API is a clear way for the browser or another service to ask for work.

Why we need itStable requests let the UI change without rewriting the planning workflow.

When to add itBefore adding My Trips or replacing sample travel data.

Travel Planner example
Today, /api/plan streams a plan and tools use sample inventory. Proposed: /api/trips and /api/conversations. Choose travel providers by coverage, freshness, licence, price, quotas and uptime. Store provider keys on the backend.

08

HTTP methods, status codes and errors

The method says what to do. The status says what happened.

Why we need itThe UI needs a clear action after each failure.

When to add itDefine these while designing each API.

Travel Planner example
GET reads. POST creates or starts work. PUT replaces. PATCH edits part. DELETE removes. Use 200 for success, 201 for creation and 202 for accepted work.

400 Bad request
401 Sign-in required
403 Access denied
404 Missing record

409 Conflicting edit
413 Upload too large
422 Invalid fields
429 Rate limit

500 App error
503 Service unavailable
504 Gateway timeout
502 Upstream failure

Proposed error body: {"code":"TRIP_CONFLICT","message":"Reload the trip before saving.","request_id":"…"}. After streaming starts, report errors as stream events. The HTTP status may already be 200.

09

Input and file upload validation

Validation checks incoming data before the app uses it.

Why we need itBad files and invalid fields can waste money or damage stored data.

When to add itAt every API boundary, before parsing or calling AI.

Travel Planner example
Today: trip text has a 4,000-character limit and uploads have a 20 MB limit. Add real file-type checks, parser limits and malware checks where needed. Treat document instructions as untrusted input. A filename extension is only one check.

10

API testing with Postman

Postman sends API requests without using the app screen.

Why we need itIt helps separate a backend bug from a browser bug.

When to add itAs soon as an endpoint exists, and after its contract changes.

Travel Planner example
Check that empty text returns 422. A greeting such as “hello” uses the current local greeting path. Test future trip APIs with two accounts. Keep tokens in private variables. Planning and uploads may make paid AI calls.

11

Exceptions, timeouts, retries and fallbacks

These rules control what happens when a step fails or takes too long.

Why we need itOne failed provider should not leave the user waiting forever.

When to add itBefore relying on external models or travel services.

Travel Planner example
Today the API maps some provider errors to safe messages. Add explicit time budgets. Retry only suitable failures. Use idempotency keys for repeated writes. A partial plan should name missing evidence. Never invent a live flight price.

12

Persistent files and user-isolated RAG

Persistent storage keeps uploaded files. RAG finds excerpts for an answer.

Why we need itFiles must survive restarts and stay inside the correct user account.

When to add itBefore hosting uploads or sharing the app with several users.

Travel Planner example
Today the app uses local uploads, ChromaDB and shared JSON keyword/graph files. Proposed: durable storage plus owner metadata in every store. Enforce isolation before retrieval. Filtering only the final answer is too late.

13

Privacy, retention and deletion

A retention policy says what we keep and for how long.

Why we need itChats and travel documents can contain private information.

When to add itBefore collecting real user data.

Travel Planner example
Explain which excerpts go to an AI provider. Add deletion jobs that track every copy. Give backups a defined expiry and document restore handling. Avoid logging passport details or full chats. Choose retention periods for the actual product.

14

Environment variables and secrets

Configuration changes between environments. Secrets grant access to services.

Why we need itKeys inside frontend code or Git can expose the account.

When to add itBefore the first external service call and every hosted release.

Travel Planner example
Today OPENAI_API_KEY loads on the backend. Keep it there. Put only public values in Vite variables. Commit .env.example with placeholders. Rotate exposed keys and remove their use. Validate required configuration at startup.

15

Dependency and security checks

Dependencies are libraries our app runs. A security scan checks known issues.

Why we need itOld or unsafe packages can expose data or break the build.

When to add itOn pull requests and on a regular schedule.

Travel Planner example
Commit the frontend lockfile. Use a reproducible Python lock or constraints file, especially for broad RAG version ranges. Review upload parsers and Markdown rendering. Keep safe HTML sanitization. A clean scan does not prove the app is secure.

16

Background jobs and long requests

A background worker runs slow work outside the web request.

Why we need itClosing a tab should not lose a long document indexing task.

When to add itWhen uploads or planning exceed reliable request time limits.

Travel Planner example
Today uploads run through the web app and may update stores partly before failure. Proposed jobs need retry limits, duplicate protection and failed-job status. A thread inside the web process is not a durable queue. Streaming shows progress but does not save a job.

17

Rate limits and AI cost controls

Rate limits cap request frequency. Budgets cap AI usage.

Why we need itOne user or a retry loop could use the whole AI budget.

When to add itBefore opening the app to public traffic.

Travel Planner example
The current graph has a recursion limit. Also cap input tokens, output tokens, parallel calls and daily spend. Include embeddings, vision, reranking and evaluations in usage. Use a shared limiter across workers. Report when the user can retry.

18

Performance, concurrency and load tests

Performance measures speed. A load test checks many users at once.

Why we need itA plan that works for one user may stall for a whole class.

When to add itAfter the basic flow works, before raising traffic limits.

Travel Planner example
Today a process lock serializes RAG access. Extra web workers do not share that lock. Check safe writes before scaling JSON stores. Use fake AI calls for most load tests. Set a small approved budget for any live provider test.

19

Unit, integration and end-to-end tests

Tests check small rules, connected parts and complete user flows.

Why we need itA saved-chat change can break planning or leak another user’s data.

When to add itAlongside each feature and each bug fix.

Travel Planner example
The project already has offline workflow and RAG tests. Extend them with realistic persistence and access checks. Use fake model responses in routine tests. Check stream errors and interrupted uploads. Keep a small separate live test for provider behaviour.

20

AI response quality and RAG evaluation

Evaluation checks whether answers are useful, correct and grounded.

Why we need itA 200 response can still contain a bad itinerary or invented fact.

When to add itBefore changing prompts, models, chunking or retrieval.

Travel Planner example
The repo has a small Ragas runner. Grow a checked reference set. Ask about the demo document’s 9:15 AM meeting. Also test missing facts, conflicting sources and hostile instructions. Track retrieval relevance, answer faithfulness, latency and cost. Model judges can make mistakes.

21

Logging, monitoring and health checks

Logs describe events. Monitoring shows trends and sends alerts.

Why we need itWe need to know where a failed plan stopped.

When to add itDuring development, then before real users depend on the app.

Travel Planner example
Today /api/health reports status and key presence. It does not prove the database or AI provider works. Add readiness checks for required local dependencies. Trace manager, workers and RAG stages. Redact prompts and secrets. Avoid paid AI calls in frequent health checks.

22

API documentation and operating guides

API docs explain requests. An operating guide explains how to run and fix the app.

Why we need itA teammate should be able to recover the service without guessing.

When to add itWhile adding each API and before handing the app to others.

Travel Planner example
Document stream events for /api/plan, upload limits and future auth rules. Explain local ports, storage locations and required variables. Add runbooks for a provider outage and a failed migration. Keep AGENTS.md focused on repo rules and required checks.

23

Backups and restoration

A backup is a recoverable copy. A restore proves the copy works.

Why we need itA deleted trip or corrupt index needs a recovery path.

When to add itBefore storing data that users cannot replace.

Travel Planner example
Define RPO: how much recent data we can lose. Define RTO: how long recovery may take. Keep source files so indexes can be rebuilt. Rebuilding may cost time and AI usage. A Git rollback restores code, not deleted user data.

24

Development, staging and production

An environment is a separate copy of the app and its settings.

Why we need itTesting a change should not damage a real user’s trips.

When to add itBefore the first hosted release.

Travel Planner example
Use the same release version in staging and production. Change configuration for each environment. Keep databases, RAG stores and AI budgets separate. Do not copy private production chats into development. A staging test should never delete a production trip.

25

Deployment platform selection

Deployment builds and runs the app on a host that users can reach.

Why we need itThe host must support our Python runtime, slow work and durable data.

When to add itChoose the host after understanding runtime and storage needs.

Travel Planner example
Proposed split: Vercel for the frontend, Railway for the Python service. Both can host Python APIs, but check execution limits and storage needs. Local RAG files need durable storage. Keep staging isolated and restrict access.

Official sources: Vite on Vercel · Function storage · Railway FastAPI · Railway volumes. Checked 23 Oct 2026.

26

Domains, HTTPS and CORS

A domain names the app. HTTPS encrypts traffic. CORS sets browser access rules.

Why we need itThe hosted browser must reach the correct backend safely.

When to add itWhen wiring the staging and production URLs.

Travel Planner example
Today Vite proxies /api to localhost:8002. That dev proxy does not ship with the built files. Configure a hosted reverse proxy or API base URL. If origins differ, allow the exact frontend origin. CORS does not replace authentication. Credentialed requests need careful cookie and CSRF rules.

27

GitHub Actions and CI/CD

CI checks each change. CD delivers a checked version to a hosted environment.

Why we need itA repeatable release reduces manual mistakes.

When to add itOnce checks work locally and a staging host is ready.

Travel Planner example
Use protected branches and scoped deployment secrets. Routine CI uses fake AI responses. Run database migrations as a controlled release step. Prevent two production releases from racing. Keep a failed check from promoting the change.

28

Build, deployment and redeployment

Deployment runs a release on a host. Redeployment releases a changed version.

Why we need itA good release keeps user data safe and gives us a way back.

When to add itFor the first hosted release, then after every approved change.

Travel Planner example
Frontend: npm ci, then npm run build. Publish dist. Backend: install locked dependencies and run Uvicorn on 0.0.0.0 with the host PORT. Set secrets and persistent storage. A Vite dev server is for local work.

Release checks: load the page, check /api/health, reopen a saved trip and verify access rules. Rehearse migrations and recovery. A code rollback cannot undo every schema change. Railway volume releases may have brief downtime. Healthcheck and volume notes.
