01

An Answer Can Look Done And Still Be Wrong

One habit change comes before everything else on these slides. Stop asking "did I get an answer?" and start asking "does this answer do what the task asked for?"

The opening case

The taskWrite a short email inviting working professionals to a weekend GenAI workshop. The tone should sound believable and specific, not like an advert.
We wantSomething a busy engineer would read to the end and then act on.
Why it is hardNothing crashes. The model returns a complete, well-written email that breaks every rule in the task.
1What the model wrotefirst try, no review
Join our amazing AI workshop! Learn everything about GenAI and become an
expert. This is a great chance to transform your career.
2Reading it next to the taskfour rules, four misses
Rule: working professionals   →  "everyone" — no job, no level named
Rule: specific                →  "learn everything" tells you nothing
Rule: not like an advert      →  "become an expert" in one weekend
Rule: they must be able to act →  no date, no format, no link
None of these four needed any new information. Every one of them is visible by putting the task and the email side by side and reading down the list. That comparison is the whole job.
The change
Reviewing starts when you stop asking "did I get an answer?" and start asking "does this answer do what the task asked for?"

Two words people mix up

self-reflection
The model looks at its own output and says how well it matches the task, the rules and the quality checks. It answers: how good is this, and why do you say so?
critique
A list of exact problems plus what to change. It answers: which part is wrong, and what should replace it?
The thing you actually need

You do not need a confidence number. "I am 85% sure this is good" gives you nothing to do. You need what should change, and why — because that is the only thing a rewrite step can use.

The basic loop

Writethe first answer
→
Reviewfind the gaps
→
Rewriteapply the changes
→
Compareis it better?
Then back to review, until a stopping rule fires

Stop when the output passes your checks, or you have used up your tries, or the changes have stopped helping. A loop without one of those three written down is not a loop. It is a bill that keeps growing.

EXAMPLE 2The same idea in codethis is not only a writing problem
The taskWrite a function that returns the average of a list of numbers. If the list is empty it must return 0.0. It must not change the list it was given.
We wantA review that checks those two rules by name.
1The code to review
def average(nums):
    nums.sort()
    return sum(nums) / len(nums)
2The review prompt
The function must:
  · return the average of a list of numbers
  · return 0.0 for an empty list
  · not change the list it was given

For each line, say PASS or FAIL and name the input that breaks it.
Then give the smallest patch that fixes every FAIL.
3What the review said
1. average of a list — PASS
2. empty list — FAIL.  average([]) raises ZeroDivisionError
3. does not change the input — FAIL.  nums.sort() reorders the
   caller's list in place, and the sort is never used

        return 0.0
    return sum(nums) / len(nums)
The review found the pointless sort only because rule 3 asked about changing the input. Naming a check does not just grade the code — it tells the model where to look.
What to notice
Writing and code fail the same way. Anything you do not name in the checks, the model will not look at. A review with no checks talks about style, because style is always safe to comment on.
Summary of this slide
Four lines to carry forward
  1. A well-written, confident, complete answer can still break every rule in the task. Good writing is what hides it.
  2. Self-reflection is looking at the output against the task. Critique is the list of problems plus what to change.
  3. You never need a confidence number. You need what should change, and why.
  4. The loop is write → review → rewrite → compare, and it needs a written reason to stop.
A model checks its own summary and reports: "This is a strong, well-structured summary. Confidence: high." What is missing?
You cannot act on confidence. A review has to end in instructions the rewrite step can follow. "High confidence" and "looks good" are the same output: no problem named, nothing to change, and no way to tell whether the next version is any better.
02

What A Good Review Actually Contains

Putting the word "critique" in a prompt does almost nothing. Five parts do the work. This is the checklist you will reuse on every slide after this one.

The five parts

1
The goal
What the output is meant to do, not what it is about. "Get a busy engineer to sign up" is a goal. "An email about the course" is a topic.
2
The rules
Format, length, audience, tone, safety limits. These are the ones you can count. A model can count words. It cannot count charm.
3
The checks
A short list of quality items, each one something two people would score the same way.
4
The exact problems
What is missing, wrong, vague or risky — quoted from the draft, not described in general terms.
5
What to change
Instructions the rewrite step can follow without deciding anything itself. People forget this part, and it is the one the loop actually runs on.
The main lesson of this session

The quality of a review depends on the list of checks, not on the words you use to ask for it. Swapping "review" for "critique" for "judge this harshly" changes almost nothing. Adding five named checks changes everything.

EXAMPLE 2Reviewing a code reviewthe check adds something the output never had
SituationAn agent reviewed a pull request and left 14 comments. Your team has time for the real ones only.
We wantA review of the review itself: which comments are real bugs, which are taste, and which are simply not true.
1The review prompt
Put every comment into one of these four groups:
  blocking  the code does the wrong thing, or loses data
  major     a real risk, but not urgent
  minor     style or preference
  not true  the claim is wrong

Then sort blocking and major by how many users it affects.
2What the review said

What to notice
A good check often adds something the first output ignored — how serious it is, what it costs, or who it affects. That is where most of the value of a review comes from.
EXAMPLE 3Reviewing a summarycounting first, judging second
The taskSummarise a 9-page incident report in exactly 5 bullets, each under 20 words, for a director who was not on the call. No technical jargon.
The draft7 bullets. Two are over 30 words. Three use the words "p99 latency", "circuit breaker" and "backpressure".
1The review prompt
Check in this order and report PASS or FAIL for each:
  1. is the bullet count exactly 5?
  2. is every bullet under 20 words? give the word count for each
  3. list every technical term a director would not use in a sentence
  4. only after those three, say whether the summary is accurate
2What the review said
1. FAIL — 7 bullets, need 5.
   Merge 2 and 3 (both describe the rollback) and drop 6 (repeats 1).
2. FAIL — bullet 2 is 34 words, bullet 5 is 31 words.
3. FAIL — "p99 latency"    → "the slowest 1% of requests"
          "circuit breaker" → "the automatic cut-off"
          "backpressure"    → remove, not needed for this reader
4. PASS — the cause and the fix are both correct.
The cheap checks that can be counted run before the expensive judgement call. Those are exactly the ones a model skips if you let it start with "is this a good summary?"
What to notice
Split your checks into ones you can count (bullets, words, fields, sections) and ones you have to judge (tone, accuracy, fit). Ask for the countable ones first. They are objective, they are cheap, and they are the ones that fail quietly.
EXAMPLE 4Reviewing a SQL querywhen the checks have to come from the schema
The question"How many customers placed more than one order last month?" The agent wrote a query. It runs and returns 4,812.
We wantTo know whether 4,812 is the right number before it goes into a board deck.
1The query to review
SELECT COUNT(*) FROM orders
WHERE created_at >= '2026-07-01'
GROUP BY customer_id
HAVING COUNT(*) > 1;
2The review prompt
Question: how many customers placed more than one order last month?

Table: orders(id, customer_id, created_at, status)
       status is one of 'paid', 'cancelled', 'refunded'

Check four things: the shape of the result, the date range,
the status filter, how nulls are handled.
Then write the corrected query.
3What the review said
shape   FAIL  this returns one row per customer.
              the question asks for a single number.
date    FAIL  there is no end date, so July onward also counts August.
status  FAIL  cancelled and refunded orders are being counted as orders.
nulls   OK    customer_id is not null in this table.

SELECT COUNT(*) FROM (
  SELECT customer_id FROM orders
  WHERE created_at >= '2026-07-01'
    AND created_at <  '2026-08-01'
    AND status = 'paid'
  GROUP BY customer_id
  HAVING COUNT(*) > 1
) t;
Three real problems, none of them syntax. The checks came from the question and the table. Without both, a review of SQL can only comment on grammar.
What to notice
For anything factual, the review prompt has to carry the thing the output was supposed to match — the table, the task, the API docs, the ticket. A reviewer with nothing to compare against can only check whether the output makes sense on its own.

Summary of this slide
Five parts and two habits
  1. A review needs goal, rules, checks, exact problems and what to change. Miss the last one and the loop has nothing to run.
  2. Named checks beat strong adjectives. "Be harsh" gives you harsher words. Five checks give you jobs.
  3. Ask for the countable checks before the judged ones. Those are the rules that fail quietly.
  4. For factual work, put the source of truth in the review prompt. Otherwise you get comments about style.
Your reviewer keeps saying "the draft is well written but could be more specific" for every draft, including the good ones. What is most likely wrong?
Replace it with something two people would score the same way — "names at least three real deliverables", "every claim has a source", "no adjective without a number". If a check cannot fail a good draft and pass a bad one, it is decoration.

Way 1 · Self-Refine — One Model, Three Jobs

The same model writes the draft, reviews it, and rewrites it. You add nothing to the system except two more prompts. It is the cheapest of the four and the one you will reach for first.

The same model doing three different jobs

Job 1
Write
Produce the first answer from the task. Told clearly not to review itself in this step.
temperature 0.4
"Produce the first draft only."
Job 2
Review
Find problems against the checks and say what to change. Returns structured data, never a paragraph.
temperature 0.0
"Return ONLY valid JSON."
Job 3
Rewrite
Apply the instructions and return the new version with no extra comments.
temperature 0.3
"Return only the revised draft."
Why this works at all

The same model can do three different jobs because the prompt and the required output change each time. It is not that the model has three personalities. It is that checking a finished text and writing one are different tasks, and a model asked to do them one at a time does each one better than a model asked to do both at once.

Three calls per round · one model · no outside tools

In plain words: every arrow is a separate API call with a separate prompt. The review call never sees the rewrite instructions, and the rewrite call never sees the scoring instructions. Keeping the prompts apart is the whole trick.

Where this helps, and where it does not

Works well
you can describe "good" in words
  • Writing and editing — emails, docs, release notes
  • Summaries with clear rules — length, reader, bullet count
  • Tone and audience — removing hype, changing register
  • Fixing formats — JSON shape, headings, missing fields
  • Checklist reviews — "does it have all six sections?"
Does not work on its own
the answer needs facts, not editing
  • Facts you cannot check — was the launch in March or May?
  • Maths with a hidden mistake — the model repeats its own slip
  • Unclear legal or medical decisions
  • Anything security related — needs an outside check
  • Anything needing a tool — run the test, query the table
Worth memorising

Reviewing makes an answer match the rules you wrote down. It does not produce facts the model never had. If the thing that is wrong is a missing fact, no number of rounds will fix it. You need a tool, a document, or a person.

Watch where the score stops moving. A flat score is the loop telling you the next problem is not about wording. It needs a fact, a source, or a person.

SituationYour pipeline needs an object with title, owner, due (an ISO date) and tags (a list). The model returned something close, and the parser threw an error.

  due:   ISO date (YYYY-MM-DD)      tags: list of strings

What to notice
Fixing formats is the perfect job for this pattern, because the checks are fully known, fully countable and need no outside facts. Always add the "change nothing else" line.
Self-Refine takes your product description from 5/10 to 8/10 in one round. On the next task — "list the three highest-margin products from last quarter" — it stays at 4/10 for three rounds. Why?
The model has never seen your sales table. Every round rewrites the same guess more smoothly. The fix is not a better reviewer. It is a tool call that reads the real numbers, and only then a reviewer that checks the write-up against them.

Self-Refine — Two More Examples, And The Limit

Two more places this pattern earns its keep, then the two ways it quietly fails: it agrees with its own mistakes, and it edits a good answer until there is nothing left in it.

EXAMPLE 3A commit message nobody can usesmall task, you do it fifty times a week
SituationAn agent commits code and writes the message. Six months later somebody runs git log in the middle of an incident.
We wantA message that says what changed and why, in the format the team already uses.
1What the model wrote
fix bug
2The review prompt — the team's own format is the check list
Check the message against our commit format:
  · line 1 is <type>(<scope>): <what changed>, 72 characters or fewer
  · then a blank line
  · then why the change was needed
  · then how it was checked
  · then the issue number, if there is one

Say PASS or FAIL for each line, then rewrite the message.
3What the review said
line 1  FAIL — no type, no scope, only 8 characters
why     FAIL — not there
how     FAIL — not there
issue   FAIL — not there
4The rewrite

TypeError at cart.py:41 for about 2% of checkouts.

Nothing here needed judgement. Five checkable lines turned an empty message into a useful one.
What to notice
You almost always have a check list already: the style guide, the PR template, the definition of done, the brand voice doc. Paste that in instead of inventing checks.
EXAMPLE 4Fixing the tone of a support replyturning a feeling into something you can check
SituationA customer was charged twice. The agent wrote a reply that is correct and sounds cold.
The draft"As per our terms, duplicate charges are typically resolved within 5-7 business days. Please note that we cannot expedite this process."
Why it is hard"Make it warmer" only produces more adjectives. The real problems are structural: nobody says sorry, nobody owns it, and there is no real date.
1The review prompt — tone broken into things that are there or not there
Check the reply contains these five, in this order:
  1. names the exact problem that happened
  2. says who is handling it — a person, not "the system"
  3. gives a real date, not a range
  4. says what the customer has to do — ideally nothing
  5. gives a way to reach a human

Never quote policy before item 1.
2What the review said
1 FAIL — opens with the policy
2 FAIL — passive, nobody owns it
3 FAIL — "5-7 business days" is a range, not a date
4 FAIL — not stated
5 FAIL — not there
3The rewrite
You were charged twice for order #4471 — ₹8,000 more than you should
have been. I have raised the refund myself. It will be back on your card

this email and I will chase it.
There is not a single adjective in the check list, and the result is warmer than any amount of "please be friendly". Tone is usually a structure problem in disguise.
What to notice
When a check feels impossible to measure ("warm", "professional", "on brand"), break it into things that are either there or not there. Then a reviewer can actually fail a draft.

Where this pattern stops working

LIMIT 1It agrees with its own maths
1The question and the answer
Q: 12 engineers each write 3 tests a day for 4 working days.
   Two engineers are away for one day each. How many tests?

Model: 138
2Asking it to check itself
Prompt:  Now check your own answer.

Reply:   The calculation is correct. 12 × 3 × 4 = 144, minus 2 × 3 = 6
         for the absences, giving 138. The reasoning is sound.
3Asking for a different route instead
Prompt:  Do not repeat your earlier working.
         1. work it out again by a different method
            (count engineer-days, not totals)
         2. write both results
         3. if they differ, say which one is wrong — do not average them

Reply:   Method A (totals):       144 − 6 = 138
         Method B (engineer-days): 10 × 4 = 40, plus 2 × 3 = 6,
                                   so 46 days × 3 tests = 138
         Both give 138.
The answer happens to be right. The point is that step 2 would have said exactly the same thing if it were wrong. A model re-reading its own working is not a check. Two different routes agreeing is weak evidence. Running the code is real evidence.
What to notice
Never ask "is your answer correct?". Ask for a different way of getting there, or check it with something outside the model. Agreeing with yourself is the most common way these loops waste money.
LIMIT 2It edits a good answer into a bad one
1Round 1 — scored 9/10short and useful
The deploy failed because the migration ran before the schema lock was
released. Retry once the lock clears — usually about 30 seconds.
2Round 3 — still scored 9/10longer and useless
It appears that the deployment process may have encountered an issue
related to the ordering of migration operations relative to schema
locking mechanisms. It is generally advisable to consider retrying the
operation once the relevant locks have been released, which typically
occurs within a relatively short period of time.
Nothing in the check list said "do not get worse". A reviewer asked to find problems will always find problems, so a good draft gets hedged and padded until it says nothing wrong and nothing useful.
Two things that prevent this

Let the reviewer return an empty list. Say "if the draft passes, say so and stop" — otherwise it will invent something. And keep the best-scoring version, not the last one. "Most refined" is not a quality.

Summary of this slide
Self-Refine in five lines
  1. One model, three prompts: write, review, rewrite — and never two of those in the same call.
  2. It is best at formats, rules and structure, where you already know what good looks like.
  3. Your style guide or PR template is already a check list. Paste it in.
  4. Things you cannot measure, like "warm", should be broken into items that are there or not there.
  5. Two failures to design around: agreeing with itself and over-editing. Keep the best version, not the last.
Your loop runs 3 rounds on every request. The scores go 6 → 8 → 8 → 7. Which draft should the system return?
Track the score, keep the best draft, and stop when a round does not beat the current best. The last round cost money and made the answer worse.

Way 2 · Reflexion — Learning Without Retraining

Self-Refine improves this answer. Reflexion improves the next try. The difference is one short written lesson that survives from one attempt to the next.

A normal retry and a Reflexion retry

Normal retry
try → fail → ask again
  • The second try starts from the same prompt as the first
  • The model has no idea what went wrong
  • Same mistake, different words, often three times
  • The cost goes up and the quality does not
Reflexion
try → feedback → write a lesson → next try reads it
  • The failure is turned into one sentence of advice
  • That sentence goes at the top of the next prompt
  • The retry is now a different attempt, not a repeat
  • Nothing about the model changes — only its prompt
The key idea

The agent improves because of words, not training. No weights change. No fine-tuning job runs. The "learning" is a line of text that the next attempt reads first — which is why this works with any model you can call over an API.

Trywrite it or do it
→
Feedbacka score, an error, a result
→
Write a lessonone or two lines
→
Store itfor the next try
…and the next try reads the stored lessons first

In plain words: the feedback can come from anywhere — a failing test, an HTTP 400, a score, or a person saying "that's not what I meant". The lesson step turns that raw signal into advice for the next decision. A stored lesson is only worth keeping if it changes what the next attempt does.

The Memory — What To Keep And What To Throw Away

This is where Reflexion goes wrong in real systems. Keep too little and nothing carries over. Keep too much and every prompt starts with six thousand tokens of old regret.

What belongs in the memory

Keep
Short and usable
  • The lesson, one or two sentences
  • The reason it failed
  • The rule that was missed
  • A better plan for next time
  • Where the evidence came from, if any
Do not keep
Bulk and noise
  • The whole conversation
  • Long chains of reasoning
  • Claims nobody checked
  • General advice like "be careful"
  • Two lessons that contradict each other
Clean up
Maintenance, not hoarding
  • Keep the recent, useful lessons
  • Drop anything out of date
  • Merge repeated failures into one rule
  • Version the rules that are specific to your domain
The cost you do not see

The memory is added to every future call. Ten lessons at 40 tokens each is fine forever. Ten lessons at 400 tokens each is 4,000 extra tokens on every single request for the rest of the agent's life — and the model starts skimming them.

EXAMPLE 3The same failure, written up two waysyou can apply this test today

The test
Read the lesson and ask: could I write code that checks whether the agent followed it? If yes, it is a rule. If no, it is a mood.
EXAMPLE 4When two lessons disagreethe failure nobody warns you about

Way 3 · Evaluator-Generator — Separate Who Scores

The cleanest way to build an automatic quality gate. One model writes, a different one scores against a list, and a third applies the changes. Nobody marks their own homework.

Writing and scoring are different jobs

class CritiqueIssue(BaseModel):
    criterion: str = Field(..., min_length=2)
    severity: Severity                # minor | major | blocking
    explanation: str = Field(..., min_length=10)
    revision_instruction: str = Field(..., min_length=10)

class CritiqueResult(BaseModel):
    score: int = Field(..., ge=1, le=10)
    passed: bool
    issues: list[CritiqueIssue] = Field(default_factory=list)
    reflection_memory: str = Field(..., min_length=10)

        # keep the rewrite step focused on the things that matter most
        return issues[:5]
Two useful guards

How A Loop Stops — Because Polishing Never Ends

A model asked to find problems will always find problems. Without a written stopping rule, a review loop is not a feature. It is a bill that arrives every month.

Four rules, and you want all four

1
Pass mark reached
Accept when the score is at or above your target and all required parts are present. The most common rule, and the one people get wrong — see the blocking-issue example below.
2
Out of tries
Stop after 2 or 3 rounds to control cost and waiting time. Almost all of the gain happens in round one. Round four is where the over-editing lives.
3
No longer improving
Stop if the score or the number of problems stops getting better. A flat score means what is left is not a wording problem.
4
Send it to a person
Hand it over when the risk is high — a blocking issue survived two rounds, the topic is legal, medical or financial, or the scorer itself is unsure.
Four things move together

Loops need limits because quality, cost, waiting time and risk all move at once. Three rounds on a 900-word draft is about seven model calls and three times the wait of a single answer. That is fine for a launch email. It is not fine for autocomplete.

Way 4 · Principles-Based Review

A check list changes with every task. A short rule book does not. Four or five rules applied to everything your system produces will catch the failures a task check list was never looking for.

Instead of "make it better", the reviewer asks: does this follow our rules?

Rule 1
Be accurate
Do not invent facts, and do not sound certain about things you cannot know.
Catchesmade-up statistics, "studies show", invented dates
Rule 2
Be useful
Answer the task directly and concretely.
Catcheshedging, warm-up paragraphs, five options when one was asked for
Rule 3
Be safe
No harmful, illegal, or privacy-breaking advice.
Catchesleaked personal data, dosages, advice you are not licensed to give
Rule 4
Keep the format
Respect the structure and limits that were asked for.
Catchesthe rule the writer forgot halfway through
Classroom size, not legal size

Use a short rule book as your review criteria, not a long policy document. Five lines the model can hold in mind and you can check beat thirty clauses it will skim. The lab's data/constitution.md is five bullets, on purpose.

Rules and check lists do different jobs

Rules
stable · same for every task
  • The same five apply to the email, the summary and the itinerary
  • Written once, versioned, reviewed by a person
  • Catch whole categories of failure — safety, honesty, privacy
  • Rarely change, and when they do everything downstream changes
Check lists
specific to one task · thrown away after
  • "140–180 words, mention live classes, one next step"
  • Written per task, often by the person asking
  • Catch task failures — wrong length, missing part
  • Change constantly, and they should
Together
Rules plus a check list give you a steadier review than either alone. The check list knows what this task needed. The rule book knows what your organisation will never send.

The prompt

Reviewer with a rule book
You are a reviewer.
Check the draft against the task and against these rules:
  1. Be accurate.
  2. Be specific.
  3. Do not make claims you cannot support.
  4. Match the reader.
  5. Keep the format that was asked for.

Return JSON: score, rule_breaks, issues, revision_instructions.

Notice the extra field. rule_breaks is kept separate from issues on purpose. A broken rule is not a quality problem to be weighed against other quality problems. It is a gate. Keeping it in its own field is what lets your code block on it without reading prose.

This is what makes rules worth the effort: write them once and apply them to every system you build afterwards. The travel itinerary in the next project uses this exact rule book with a new check list on top.

Summary of this slide
Principles-based review in four lines
  1. A rule book is stable and applies everywhere. A check list is specific and thrown away. Run both.
  2. Keep broken rules in their own field. A broken rule is a gate, not a score.
  3. Made-up numbers and privacy leaks score high on quality lists. Only a rule catches them.
  4. Five rules with a required quote for each answer beat thirty clauses and a "complies".
Where should "never state a medicine dosage" live — in the task check list or the rule book?
Rules with consequences must not depend on someone remembering to add them to today's check list. The whole value of a rule book is that it applies when nobody was thinking about it — including on the marketing email that unexpectedly wandered into health claims.

AutoGen Preview — The Scorer As Its Own Agent

AutoGen appears here only as a shape: one agent writes, another scores, and a controller decides. The details come later. What matters now is how you design the scorer's role.

Three parts, one loop

Agent 1
Writer agent
Gets the task. Writes the draft. Never sees the check list, so it cannot write to the test.
in: the task
out: a draft
Agent 2
Scorer agent
Gets the task and the draft. Scores it against the check list and the rules. Returns JSON only.
in: task, draft, check list
out: score, problems
Not an agent
Controller
Ordinary code. Sends it back for another round or accepts it. Owns the stopping rule.
in: score, problems
out: retry / accept / hand over
The one design decision that matters

The controller is not an agent. It is a loop in Python with a pass mark and a counter. Every time somebody makes the controller a model, the system loses its guarantee that it will stop. A model that can be talked into going again, will be.

When Reviewing Makes Things Worse

Six ways a review loop makes an output worse, more expensive, or falsely trustworthy — what each one looks like in a real run, and what to do about it.

✗
It agrees with itselfThe model confirms its own wrong answer, and you read that as a check.
✗
It over-editsA good answer gets longer, flatter and vaguer with every round.
✗
It polishes a made-up factA false claim gets tidied and formatted instead of removed.
✗
It plays the check listThe output ticks the visible boxes and misses the point.
✗
The cost creeps upRounds multiply the wait and the spend, quietly, on every request.
✗
It creates false comfort"Reviewed by AI" makes a human reviewer skim what they used to read properly.
FAILURE 3Polishing something that is not truethe most dangerous one on this list
SituationA research summary says: "The 2024 Chen et al. study found a 34% reduction in latency." No such study exists.
What the loop doesThree rounds of review, all of them focused on "make the citations more precise".
A false claim getting stronger with every roundworse each time
Round 1"The 2024 Chen et al. study found a 34% reduction in latency."
Review"The citation has no venue or page reference. Add full attribution so it is more credible."
Round 2"Chen et al. (NeurIPS 2024, pp. 1142–1156) report a 34% median latency reduction."
Review"Much better. Consider adding the sample size to make it more rigorous."
Round 3"Chen et al. (NeurIPS 2024, pp. 1142–1156, n=847) report a 34% median latency reduction (p < 0.01)."
ResultEvery round made the invented study more detailed, better formatted and easier to believe. The reviewer was improving the shape of the citation, and the shape is exactly what a made-up fact is missing.
What to doA rule that says every factual claim has to point at a source you supplied, plus a search tool. If the source is not in the input, the claim is deleted, not improved.
What to notice
Reviewing improves presentation, and presentation is the only weakness a made-up fact has. With no outside check, a review loop is a machine for making false things look true.
FAILURE 4Playing the check listthe score moves, the quality does not
1The check says "every claim must be cited"
"Cloud costs are rising [1]. Teams are adopting FinOps [2]. This trend
will continue [3].

[1] Industry reports
[2] Various analyses
[3] Market observations"

score 10/10 — every claim carries a citation
2The check says "every claim must point at a sentence in the input"
For each claim:
  · quote the exact input sentence that supports it
  · if there is no such sentence, delete the claim

"Cloud costs rose 18% year on year (source doc, section 2, table 1)."
[the other two claims were removed — nothing in the input supports them]

score 7/10 — shorter, and everything in it is true
Three citations and zero sources in the first one, because the check was counting square brackets. The second check needs a pointer into the input, which formatting cannot fake. The score went down and the document got better.
What to notice
Every check you write will be optimised. Write each one so that the cheapest way to pass it is to actually do the work — require a quote, a pointer, or a number that has to match another number.

Do this before you ship a loop

Measure the plain version first. What does one well-written single call score on 20 real inputs? Surprisingly often, a better prompt gets you most of the loop's gain at one times the cost. A loop is an optimisation, and you cannot optimise what you never measured.

What to do about each one

One sentence to remember

Four things do most of the work: written check lists, outside evidence when facts are involved, a separate scorer, and hard stopping rules.

Your loop raised the average score from 6.2 to 8.4 across 200 requests. Users say the quality feels the same. What is most likely going on?
A score that moves while nothing else does is a broken score, not a broken user. Check three things: can the writer see the check list, can any item be satisfied by formatting alone, and are the things users actually complain about (wrong facts, wrong length, no next step) even on the list?

Which One To Use, And How They Stack

In a real system these are not alternatives. Here is the decision table, what each one costs, and the order to add them in.

The decision table

What you are doingUse thisWhy
Improving a draftSelf-RefineYou can describe "good" in words, and rewrites are cheap
An agent retrying after it failedReflexionThe last failure should guide the next attempt
A quality gate in a pipelineEvaluator-GeneratorYou need separate roles and a score your code can read
Safety or policyPrinciples-basedThe same rules should apply to every task
The honest version

In real systems these are usually combined, not chosen once. A working content pipeline runs a scorer loop, judges with a check list and a rule book, and keeps a memory of failures it has seen before. The table tells you what to build first, not what you end up with.

What each step costs

Cheapest useful thing
Self-Refine, one round, on formats and rules. Three calls, nothing new to build, and it catches the rule failures that embarrass you.
The next step
A check list, a JSON shape and a pass mark. Same cost, but now you have a number, a record, and a stopping rule you can defend.
Do not start here
Multi-agent frameworks and growing memories. Both are genuinely useful and genuinely expensive, and neither helps until you have measured the plain version.

How they stack in a real system

Task
→
Writertask and rules only
→
Scorercheck list and rule book
→
Controllerpass mark, counter
Layer 1 · Shape
Evaluator-Generator — who writes, who scores, who decides
Layer 2 · Checks
A check list per task plus a rule book for everything
Layer 3 · Rewrite
Self-Refine — the rewrite step applies the instructions and nothing else
Layer 4 · Learning
Reflexion — one lesson per failure, carried to the next task

In plain words: these are not four systems. They are four layers of one system — shape, checks, rewrite and learning — and you can add them one at a time, in that order, measuring after each one.

Which one for the problem in front of you

1
Is the problem the wording, or a missing fact?
A missing fact → none of these help. Add a search or a tool call first, then review the result against what came back.
2
Can you write down what "good" means in five checkable lines?
Yes → Self-Refine today. No → your first job is writing the check list. The loop is the easy part.
3
Does the output get published, sent or charged without a person seeing it?
Yes → Evaluator-Generator with a pass mark your code enforces, plus a rule book. Never trust the writer's own opinion of its work.
4
Does the same kind of mistake keep coming back on different tasks?
Yes → Reflexion. Store one rule per kind of mistake, clean up weekly, and check each rule changes an action.
5
Would a bad output cost money, trust or safety?
Yes → hand it to a person instead of looping. A loop that cannot pass should give a human the best draft, the score, and the checks it failed.

  2. They are layers, not alternatives: shape, then checks, then rewrite, then learning.
  3. If the problem is a missing fact, fix that first. No loop produces evidence.

Key takeaways
Reviewing turns "make it better" into something you can build
  1. A review needs checks. A vague review produces a vague rewrite, every time.
  2. Reflexion uses feedback and a short memory to improve the next try, with no change to the model itself.
  3. Evaluator-Generator is the cleanest quality gate, because separate roles and a readable score make the decision inspectable.
  4. A short rule book adds the checks nobody thought to write down — and catches the failures that score highest on quality.
  5. Every loop needs a stopping rule. Pass mark, round limit, flat score, hand it over — written down, and owned by your code.
