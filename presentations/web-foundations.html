01

The Whole Picture

Before any of the parts, the shape. Every app you have ever used is the same four boxes, in the same order, every single time.

Think of a bank branch

You want your balance. You do not walk into the vault. You go to the counter, ask, and the counter staff go and find out.

The counter
Where you stand. Forms, signs, a person who takes your request. This is the frontend.
The back office
Checks who you are, checks the rules, decides what you are allowed to see. This is the backend.
The ledger
The actual record of every account and every transaction. This is the database.
You only ever see the counter. Everything else happens where you cannot reach it — deliberately

The one sentence to hold on to

The frontend asks. The backend decides. The database remembers.

Everything for the rest of this session is a detail hanging off that sentence.

Why split it up at all?

A fair question. Why not just let the page talk to the ledger directly?

  • Trust. The frontend is on the customer's machine. They can change it. Anyone determined enough can open a browser's developer tools and edit the page. So nothing that matters can be decided there.
  • One truth. The website, the phone app and the partner bank's system all ask the same backend. One set of rules, not three.
  • Safety. The database is never exposed to the outside world. Only the backend can reach it, and only through the specific questions it knows how to ask.
The mistake this prevents

Imagine the discount on a trading fee were calculated in the browser. A user edits the page, sets the discount to 100%, and submits. If the backend simply trusts what arrives, the trade goes through free.

This is why the rule is absolute: the frontend is a display, never an authority. Every check that matters is repeated on the server, even if the page already did it.

02

HTML — The Structure

The bones of the page. What things are, and in what order. Not what they look like — that comes next.

It is a set of labelled boxes

HTML marks up your content so the browser knows what each piece is. This bit is a heading. This bit is a paragraph. This bit is a button.

Think of a printed form: there is a title at the top, some labelled fields, and a signature box. HTML is you writing down that layout.

html · a tiny page
<h1>My Portfolio</h1>

<p>Total value: 12,40,000</p>

<input id="amount" placeholder="Amount to invest">

<button>Invest</button>

That is a real page. Open it in a browser and you get a heading, a line of text, a box to type in, and a clickable button. Plain and grey, but working.

Reading the syntax

Almost everything comes in a pair — an opening tag and a closing tag with a slash. What sits between them is the content.

<h1> … </h1>
A heading. h1 is the biggest, down to h6. Use one h1 per page.
<p> … </p>
A paragraph of text.
<div> … </div>
A plain container. Means nothing on its own — it exists to group things so you can position or style them together.
<input>
A box the user types into. No closing tag, because there is nothing to put inside it.
<button> … </button>
A thing you can click.
id="amount"
A name tag. Lets the styling and the code find this exact element later. Must be unique on the page.

Boxes inside boxes

Real pages nest. A card contains a heading, some text and a button — so you wrap them in a container and the whole thing moves as one.

html · one card
<div class="card">
    <h3>HDFC Bank</h3>
    <p>120 shares · 1,680 each</p>
    <button>Sell</button>
</div>

Note class="card". Where id names one specific element, class is a group label — you can put class="card" on fifty holdings and style all fifty at once. That is the whole point of it.

What HTML is not

HTML is not a programming language. It cannot add two numbers, make a decision, or repeat something. It has no logic in it at all.

It is a description of structure, and nothing more. That is genuinely all it does, and it is why it takes an afternoon to learn the basics.

You want to style all forty holdings in a portfolio the same way. Do you give them an id or a class?
A class. An id names one unique element — useful when code needs to find that exact box. A class is a group label, so one styling rule reaches every holding at once. Forty ids would mean forty copies of the same styling rule, and forty places to change when the design does.
03

CSS — How It Looks

Same content, different appearance. CSS is the branding sheet: colours, spacing, fonts, where things sit.

Point at something, then describe it

Every CSS rule is two halves. Which elements you mean, then what they should look like.

css
.card {
    background: white;
    border-radius: 12px;
    padding: 20px;
    border: 1px solid #e4e0d6;
}

button {
    background: #c96442;
    color: white;
    padding: 10px 18px;
}

The first rule says: find everything labelled "card", give it a white background, round the corners, put 20 pixels of space inside it, and draw a thin line around it. The second says: make every button clay-coloured with white text.

The words you will meet most

PropertyControlsExample
colorThe colour of the text itselfcolor: #1f1e1c
backgroundWhat is behind itbackground: white
paddingSpace inside the box, around the contentpadding: 20px
marginSpace outside the box, pushing others awaymargin: 12px
font-sizeHow big the text isfont-size: 16px
borderThe line around the edgeborder: 1px solid grey
display: flexLay the children out in a rowThe usual way to arrange things

Padding versus margin catches everyone at first. Padding is the gap between a box's edge and its contents — like the white space inside a printed form's field. Margin is the gap between this box and the next one.

Colours look odd at first

You will see things like #c96442. That is a colour written in hexadecimal: two characters of red, two of green, two of blue. #000000 is black, #ffffff is white. You never work these out by hand — every design tool hands you the code.

Why this is kept separate

The content lives in HTML. The appearance lives in CSS. Change the CSS file and the entire product is rebranded — every page, every screen — without touching a single word of content.

That separation is why a company can roll out a new visual identity in days rather than rewriting everything.

A useful reference point

The deck you are reading right now is HTML for the words and structure, and about 250 lines of CSS for everything you can see — the dark background, the serif headings, the coloured boxes, the layout.

That is the whole thing. There is no other magic in the appearance.

04

JavaScript — How It Reacts

HTML and CSS give you a poster. JavaScript is what makes it respond when you touch it. This one is a real programming language.

It waits for things to happen

Most frontend code is the same shape: when the user does X, do Y. A click, a keystroke, a page finishing loading.

javascript
// find the button on the page
const button = document.getElementById("invest");

// when it is clicked, run this
button.onclick = function() {
    const amount = document.getElementById("amount").value;

    if (amount < 500) {
        alert("Minimum investment is 500");
    } else {
        alert("Investing " + amount);
    }
};

Read it in English: find the invest button; when someone clicks it, read whatever is in the amount box; if that is under 500, show a warning; otherwise show a confirmation.

The handful of ideas that cover most code

variable
A named box holding a value. const rate = 7.5. Named so you can refer to it later.
if / else
A decision. If this is true do one thing, otherwise do another. Exactly like a spreadsheet IF.
function
A named set of steps you can run whenever you want. Like a saved formula.
loop
Do the same thing for every item in a list. "For each holding, add up its value."
event
Something the user did. A click, a keypress, a form submission.
array
An ordered list of things, written in square brackets. A column in a spreadsheet.

If you have written a nested IF in Excel, or recorded a macro, you have already used every idea in that box. The vocabulary differs; the thinking does not.

Where JavaScript runs — and why it matters

It runs on the customer's machine, inside their browser. Which leads directly to the most important rule on this slide.

Never trust the browser

That if (amount < 500) check is a courtesy. It gives instant feedback without a round trip to the server. It is not security.

Anyone can open their browser's developer tools and delete that check, or send a request that skips the page entirely. The server must check the 500 minimum again, and the server's answer is the one that counts.

Check twice: once in the browser for a good experience, once on the server because it is the only one you control.

Three languages, three jobs

HTML
What is on the page. The structure. Not a programming language.
CSS
What it looks like. Colours, spacing, layout. Also not a programming language.
JavaScript
What it does. Decisions, calculations, talking to the server. A real programming language.
Your page checks in JavaScript that a transfer is under the daily limit. Is that enough?
The server must check again. JavaScript runs on the user's own computer, so they can edit it, disable it, or bypass the page completely and send the request directly. Browser checks make the app pleasant to use. Server checks make it correct. You need both, and only the second one is enforcement.
05

JSON — The Shared Language For Data

When the frontend and the backend send each other information, it is almost always written this way. It is far simpler than it looks.

It is a labelled record

Think of a single row of a spreadsheet, written out with its column headings attached so it can travel on its own.

json · one holding
{
  "symbol": "HDFCBANK",
  "quantity": 120,
  "price": 1680.50,
  "sector": "Financials",
  "is_pledged": false
}

Curly brackets open and close the record. Inside, each line is a name, a colon, and a value, separated by commas. You can read that without anyone explaining it, which is exactly why it won.

The rules, all of them

Value typeHow it is writtenExample
TextAlways in double quotes"HDFCBANK"
NumberNo quotes, full stop for decimals1680.50
Yes or notrue or false, no quotesfalse
Nothingnull — the value is deliberately emptynull
A listSquare brackets, items separated by commas["NSE", "BSE"]
A record inside a recordCurly brackets again, nestedSee below

Lists and nesting

A whole portfolio is a list of holdings — square brackets around several records:

json · a list, with nesting
{
  "client": "Ravi Menon",
  "total_value": 1240000,
  "holdings": [
    { "symbol": "HDFCBANK", "quantity": 120 },
    { "symbol": "INFY",     "quantity": 80  }
  ],
  "advisor": {
    "name": "Priya S",
    "branch": "Mumbai"
  }
}

Read it top down: a client name, a total, a list of two holdings, and an advisor record tucked inside. Nesting is just a record used as a value.

Why everyone agreed on this

The frontend might be JavaScript. The backend might be Python. A partner's system might be Java. None of them can read each other's internal data directly.

JSON is the neutral middle. Every language can produce it and every language can read it, so it became the format the whole industry sends data in. It is plain text — you could type it in Notepad.

The mistakes that break it

  • A trailing comma. A comma after the last item is invalid. This is the single most common error.
  • Single quotes. JSON demands double quotes. 'HDFCBANK' is not valid.
  • Unquoted names. The name on the left of the colon must be in quotes too.
  • Comments. There is no way to write a note inside JSON. It is data only.

Miss one of those and the receiving system rejects the whole message, not just the bad line. JSON is strict on purpose — strict means unambiguous.

In JSON, how do you write the number 120 and the word Infosys?
Numbers bare, text quoted. The quotes are how the receiving system knows which is which. Put quotes around 120 and it arrives as the text "120" — so the backend may refuse to do arithmetic with it, or worse, sort it alphabetically. This distinction causes a lot of real bugs.

What A Server Actually Is

Not a mysterious black box. A computer that never sleeps, running a program that waits for questions and answers them.

The whole idea

A server is an ordinary computer with two unusual habits: it is always switched on, and it is always listening for requests. When one arrives it works out the answer and sends it back.

The word gets used for both the machine and the program running on it. In practice people mean the program.

Request arrives
→
Who is asking?
→
Are they allowed?
→
Fetch and calculate
→
Send the answer
Then it forgets you and waits for the next one. Thousands of times a second

What belongs on the server, and nothing else

Server only
never in the browser
  • Rules that matter — limits, eligibility, fees
  • Who you are — passwords, sessions, permissions
  • Secrets — database passwords, API keys
  • The real numbers — anything money depends on
  • Database access — always, without exception
Browser is fine
for speed and comfort
  • Showing and hiding things
  • Instant "this field is empty" nudges
  • Sorting a table already on screen
  • Animations and layout
  • A first check before sending

Addresses, ports and hosting

localhost
"This very computer." While building, the server runs on your own laptop and you reach it at localhost. Nobody else can.
port
A numbered door on a machine. One computer runs many programs, so each picks a door — 8000, 5173. That is what the number after the colon means.
deploy
Moving your program from your laptop onto a machine that is always on, so other people can reach it.
the cloud
Renting that always-on machine from Amazon, Google or Microsoft instead of buying and running one yourself.

So http://localhost:8000 reads as: on this computer, knock on door 8000. Once deployed that becomes a real address like https://api.yourbank.com, but nothing about how it works changes.

Static versus dynamic — worth knowing

Some websites are just files sitting on a disk being handed out — a brochure, a slide deck like this one. Nothing is calculated. That is static, and it is cheap and simple to host.

The moment a page has to look something up, check who you are, or work out a number, you need a program running. That is dynamic, and that program is your backend.

07

APIs — How The Two Halves Talk

An API is the published list of things you are allowed to ask a server for. Like the set of forms at the counter: you cannot ask for anything, only what is on a form.

An endpoint is one address you can ask

Each thing the server can do gets an address. Together they are the API.

a small API
GET     /holdings          list every holding
GET     /holdings/12       get holding number 12
POST    /holdings          create a new holding
PUT     /holdings/12       update holding number 12
DELETE  /holdings/12       remove holding number 12

Two parts on every line. The verb says what kind of action. The path says which thing. Notice the path is the same for all five — it is the verb that changes the meaning.

The four verbs

VerbMeansAt the bank counterChanges anything?
GETGive me this"Show me my balance"No — safe to repeat
POSTCreate something new"Open a new account"Yes — repeating creates duplicates
PUTUpdate what is there"Change my address to this"Yes, but repeating is harmless
DELETERemove it"Close this account"Yes, and usually permanent

That distinction in the last column is real and it matters. If your internet drops mid-request, a GET can be retried safely. A POST cannot — retry it and you may open two accounts. This is why a wobbly connection at a payment page is genuinely dangerous, and why serious systems put protections around exactly this.

What a request actually contains

a POST request, in full
POST /holdings
Content-Type: application/json
Authorization: Bearer eyJhbGci...

{
  "symbol": "INFY",
  "quantity": 80,
  "price": 1520.00
}
  • The verb and path — what you want done, and to what.
  • Headers — notes about the request. Content-Type says "the body is JSON". Authorization proves who you are.
  • The body — the actual data, as JSON. GET and DELETE usually have no body; there is nothing to send.

And what comes back

the response
201 Created

{
  "id": 13,
  "symbol": "INFY",
  "quantity": 80,
  "price": 1520.00
}

A number, then the data. The server assigned id: 13 — the frontend did not choose that, and should never try to. Identity is the server's job.

Status codes — read the first digit

CodeMeansWhose fault
200 OKWorked. Here is your answer—
201 CreatedWorked, and something new exists now—
400 Bad RequestYour message was malformed or missing a fieldThe caller
401 UnauthorizedYou have not proved who you areThe caller
403 ForbiddenWe know who you are. You still may not do thisThe caller
404 Not FoundNo such thing at that addressThe caller
500 Server ErrorSomething broke on our sideThe server

The shortcut: 2xx worked, 4xx means the caller got it wrong, 5xx means the server got it wrong. That one rule tells you which team to talk to, and it is most of what a status code is for.

Why an API is worth having at all

Once the backend publishes this list, anything can use it. The website, the phone app, an Excel macro, a partner bank, an automated report at 6am.

None of them need to know a single thing about how the backend works inside, or even what language it is written in. They only need the list of addresses and the shape of the JSON. That is the entire value of an API: the two sides can change independently, forever, as long as the agreement holds.

Your payment request times out and you never see a response. Is it safe to press the button again?
Not safe. No response does not mean no action. The server may have completed the payment and the reply got lost coming back. Retrying can pay twice. This is why payment systems attach a unique reference to each attempt, so the server recognises a repeat and refuses to act on it twice.

FastAPI — Writing The Backend

A Python toolkit for building exactly the API on the last slide. It turns "I want an address that does this" into about three lines.

An endpoint, in full

python · fastapi
from fastapi import FastAPI

app = FastAPI()

# when a GET arrives at /holdings, run this function
@app.get("/holdings")
def list_holdings():
    return [
        {"symbol": "HDFCBANK", "quantity": 120},
        {"symbol": "INFY",     "quantity": 80},
    ]

The line beginning with @ is a decorator — a label stuck on the function underneath. It reads as: "when a GET request arrives at /holdings, run the function below." That is the one piece of unfamiliar punctuation on this slide, and it means nothing more than that.

The function returns an ordinary Python list. FastAPI converts it to JSON automatically. Nobody writes the curly brackets and quotes by hand.

Reading part of the address

python · a value from the path
@app.get("/holdings/{holding_id}")
def get_holding(holding_id: int):
    return {"id": holding_id, "symbol": "HDFCBANK"}

The curly brackets in the path mark a blank to be filled in. Ask for /holdings/12 and holding_id arrives as 12.

Note : int. That says this must be a whole number. If somebody requests /holdings/banana, FastAPI rejects it with a clear 400 before your function runs at all. You did not write that check. Declaring the type was enough.

Receiving data, and checking it

python · POST with validation
from pydantic import BaseModel

# the shape we will accept. nothing else gets through.
class NewHolding(BaseModel):
    symbol: str
    quantity: int
    price: float

@app.post("/holdings")
def create_holding(holding: NewHolding):
    if holding.quantity <= 0:
        return {"error": "Quantity must be positive"}

    value = holding.quantity * holding.price   # the backend logic
    return {"symbol": holding.symbol, "value": value}

That class is a contract. Send JSON missing price, or with quantity as the text "eighty", and FastAPI refuses it with a message naming the exact field. Your code only ever runs on data that already fits the shape.

Then comes the part only the server can do: the logic. Checking the quantity is positive. Multiplying out the value. This is the "back office decides" step from slide one, and here it is in three lines.

The free documentation

Start a FastAPI server and visit /docs in a browser. You get a full page listing every endpoint, the shape of every request, and a button to try each one live — generated from the code itself.

Nobody wrote that page. It cannot go out of date, because it is built from the same declarations that run the server. For a non-engineer this is the single most useful thing in this deck: you can explore any FastAPI backend yourself, without reading code.

Where it fits

FastAPI is one of several tools that do this job. You will hear Django and Flask in Python, Express in JavaScript, Spring in Java.

They differ in style and in how much they do for you. The shape is identical in all of them: an address, a verb, a function, JSON back. Learn it once and every backend you meet is recognisable.

The Database And SQL

The server forgets everything the moment it answers. The database is the part that remembers — and this is the layer closest to what you already know.

It is a set of very disciplined spreadsheets

A database holds tables. A table has fixed columns and any number of rows. If you can picture a spreadsheet, you can picture this.

table: holdings
id | symbol    | quantity | price   | client_id
---+-----------+----------+---------+----------
 1 | HDFCBANK  |      120 | 1680.50 |        7
 2 | INFY      |       80 | 1520.00 |        7
 3 | TCS       |       45 | 3890.00 |        9

Three differences from a spreadsheet, and they are the whole reason databases exist:

  • Columns have fixed types. quantity holds whole numbers. You cannot type "eighty" into it. The database refuses.
  • Every row has an id. A permanent, unique handle. Two clients named R. Menon are still row 7 and row 41.
  • Rows point at each other. client_id: 7 means "this belongs to client number 7 in the clients table". That is how a portfolio links to its owner without copying their details onto every row.

SQL — asking the questions

SQL is the language for talking to a database. It was designed to read like English, and it very nearly does.

sql · the four operations
-- read
SELECT symbol, quantity FROM holdings WHERE client_id = 7;

-- create
INSERT INTO holdings (symbol, quantity, price, client_id)
VALUES ('INFY', 80, 1520.00, 7);

-- update
UPDATE holdings SET quantity = 100 WHERE id = 2;

-- remove
DELETE FROM holdings WHERE id = 2;

Read the first one aloud: select symbol and quantity from holdings where client id is 7. It says what it does.

The parts you will actually use

WordWhat it doesExample
SELECTWhich columns you wantSELECT symbol, price
FROMWhich tableFROM holdings
WHEREOnly rows matching a conditionWHERE quantity > 50
ORDER BYSort the resultORDER BY price DESC
LIMITOnly the first fewLIMIT 10
COUNT, SUM, AVGTotals and averagesSELECT SUM(quantity)
GROUP BYTotals per categoryGROUP BY sector
JOINPull two tables together on a shared idJOIN clients ON ...

GROUP BY is a pivot table. "Total holdings per sector" is one line of SQL and is exactly the thing you would build with a pivot in Excel:

sql · a pivot, essentially
SELECT sector, SUM(quantity * price) AS total
FROM holdings
GROUP BY sector
ORDER BY total DESC;

Who writes the SQL?

Often nobody, by hand. Most backends use a translator — an ORM — so you write Python and it produces the SQL underneath:

python · the same query, written in Python
session.exec(
    select(Holding).where(Holding.client_id == 7)
)

# the library turns that into:
--   SELECT * FROM holdings WHERE client_id = 7

It is worth understanding SQL anyway. When something is slow or a report is wrong, the SQL is what you end up reading.

The famous one — SQL injection

If a server glues user input straight into a query, a visitor can type SQL into a search box and have the database run it. That is how real breaches have dumped entire customer tables.

The fix is old and completely settled: never paste user input into a query. Pass it as a separate parameter, which every modern library does by default. This is why "we wrote our own database layer" should always prompt a follow-up question.

You want each sector's total holding value, biggest first. Which SQL words do you need?
SUM, GROUP BY, ORDER BY. GROUP BY collapses the rows into one per sector, SUM totals each group, ORDER BY … DESC sorts biggest first. It is a pivot table written as a sentence. WHERE is different — it filters individual rows before any grouping happens.

The Whole Project — CRUD

Four operations cover the overwhelming majority of business software ever written. They have an ugly acronym and you now understand all of it.

CRUD

LetterOperationVerbSQLIn a portfolio app
CCreatePOSTINSERTAdd a holding
RReadGETSELECTView the portfolio
UUpdatePUTUPDATEChange a quantity
DDeleteDELETEDELETERemove a holding

Look across each row. The verb, the SQL and the business action all line up. That is not a coincidence — the web's verbs were designed around exactly these four operations, which is why the mapping is so clean and why it is worth memorising this table alone.

How much of the world is this

A CRM, an inventory system, an HR portal, a ticketing tool, a loan tracker, a KYC system. Underneath the branding they are all lists of things you can create, read, update and delete, with rules attached.

When a vendor demos software to you, this is the first question worth asking: what are the things, and who is allowed to do which of the four to each of them? That single question maps most systems in about ten minutes.

What a small real project looks like

the files, and what each is for
backend/
  main.py        starts the server, connects the addresses
  models.py      the tables: what columns, what types
  schemas.py     what the browser may send and receive
  crud.py        the four operations, written once
  routers/       the addresses, grouped by topic
  database.py    the connection to the database file

frontend/
  index.html     the structure
  styles.css     the appearance
  api.js         every call to the backend, in one place
  app.js         what happens when the user does things

Two things worth noticing, because they are how professionals keep projects manageable:

  • Every file has one job. Tables in one place, appearance in another. When something is wrong with the styling you know which file to open without searching.
  • The four operations are written once, in crud.py, and reused for every table. Holdings, clients and sectors all share them. Write it once, fix it once.

The words, so meetings make sense

frontend
Everything running in the user's browser. What they see and touch.
backend
The program on the server. Rules, decisions, calculations.
API
The published list of requests the backend accepts.
endpoint
One address in that list, such as /holdings.
JSON
The text format both sides send data in.
database
Where it is stored so it survives a restart.
SQL
The language for asking the database questions.
CRUD
Create, read, update, delete. Most of business software.
deploy
Putting it on an always-on machine so others can use it.
full stack
Someone who works on both the frontend and the backend.

The whole session in six lines

  • Four layers. Browser, server, database, and the API agreement between the first two.
  • Three languages in the browser. HTML is the structure, CSS the appearance, JavaScript the behaviour.
  • JSON is how they talk — plain text, labelled values, readable by anyone.
  • Four verbs. GET reads, POST creates, PUT updates, DELETE removes.
  • The database remembers, SQL asks it questions. Tables are strict spreadsheets; GROUP BY is a pivot.
  • The frontend asks, the backend decides. Never trust the browser — every rule that matters is enforced on the server.
What to do with this

You are not going to go and build a trading platform this week. That was never the point.

The point is that the next time an engineer says "the endpoint returns a 500" or "that validation is only client-side" or "we need a JOIN across two tables", you know what they mean, and you can ask the next question. In a room where the business and the engineers have to agree on something, that is worth a great deal.

A colleague says "the frontend already checks the limit, so the backend does not need to". What is your response?
The backend must check too. Frontend code runs on the user's machine, so it can be edited or skipped completely — a request can be sent straight to the API with no page involved at all. The duplication is deliberate: the browser check is for a good experience, the server check is the actual rule. If you only get one, keep the server one.
