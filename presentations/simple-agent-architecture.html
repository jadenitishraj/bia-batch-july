Nine small Python files, each with one job. If you can say what a file does in one sentence, the file is the right size.

Why split it up at all?

You could write this in one file. It would work. It would also be the file nobody wants to open in three weeks.

  • You change one thing at a time. Adding a tool means touching two files, never twelve.
  • You can explain one thing at a time. This deck has a slide per file because the code has a file per idea.
  • You can test one thing at a time. test_agent.py runs the agent with no API and no browser in the way.
The rule we followed

A file is allowed to know about the files below it, never the ones above. main.py knows about agent.py. agent.py knows about the tools. No tool has ever heard of FastAPI. That is why you can run the whole agent from the terminal without a server.

The three layers

Transport
main.py and React. Moves JSON around. Knows nothing about AI.
Brain
agent.py, prompts.py, memory. Decides what happens.
Hands
tools/. Plain Python functions. They do not know an AI exists.
02

What An Agent Actually Is

A normal LLM call is a question and an answer. An agent is that same call, put inside a loop, with permission to ask for help.

Chatbot versus agent

Plain chatbot
one step
  • You ask, it answers.
  • Everything comes out of the model's head.
  • Ask it today's date and it guesses.
  • Ask it your refund policy and it invents one.
Agent
a loop
  • You ask. It may ask you to run a function first.
  • Your code runs, the answer goes back in.
  • Date comes from datetime.now(). Real.
  • Policy comes from your JSON file. Real.

The loop, in words

1
Send everything to the model
System prompt, the conversation so far, and the list of tools it is allowed to use.
2
The model replies one of two ways
Either plain text — done — or "call multiply with a=12, b=8".
3
If it asked for a tool, run it
Your Python function runs. The return value is added to the message list.
4
Go back to step 1
Now the model can see the tool result. It may answer, or ask for another tool.
Question
→
Model decides
→
Asks for a tool
→
Python runs it
→
Result goes back
↺
Repeat until the model answers in plain text
Everything else in this project supports that circle

The whole agent, in our code

We do not write the loop. create_agent already contains it. We supply three things and step back.

backend/agent.py
from langchain.agents import create_agent
from langchain_openai import ChatOpenAI

from prompts import build_system_prompt
from tools.registry import ALL_TOOLS


def build_agent():
    # 1. the model. temperature=0 means most predictable answer
    model = ChatOpenAI(model=MODEL_NAME, temperature=0)

    # 2. the system prompt, with long term memory baked in
    facts = long_term_memory.get_all_facts()
    system_prompt = build_system_prompt(facts)

    # 3. agent = model + tools + system prompt
    agent = create_agent(model, ALL_TOOLS, system_prompt=system_prompt)

    return agent, system_prompt

Words people mix up

tool call
The model does not run anything. It returns a name and arguments. Your code runs it. That gap is where every safety check lives.
turn
One trip around the loop: one model call, plus any tools it asked for.
temperature
How random the answers are. 0 for tool-using bots, so the same question picks the same tool.
agent executor
The thing that runs the loop for you. In LangChain 1.x that is what create_agent returns.
The misunderstanding to kill early

Beginners think the model executes the function. It never does. The model has no Python, no internet, no clock. It can only produce text — and a tool call is just a very structured piece of text that says "please run this for me".

You give the agent a delete_all_users() tool and the model asks for it. What runs it?
Your own process. The model only produced the words "delete_all_users, no arguments". Your machine is what actually deletes. Nothing blocks it for you — if a tool is in the registry, it is a thing the model can make happen. The registry is a permission list.
03

The System Prompt

The job description. It goes in before every single question, and it is the cheapest way to change how your agent behaves.

Our actual prompt

backend/prompts.py
SYSTEM_PROMPT = """You are "Bia", a helpful assistant.

You can use tools. Rules for using tools:

1. For any math, always use the math tools. Never do the math in your head.
2. For questions about company products, policies, pricing or support,
   use the tool `search_knowledge_base` to find documents first.
   Then answer using ONLY what those documents say.
3. If the user asks you to remember something about them
   (example: "remember that I like Python"), call the tool `remember_fact`.
4. If the user asks what you know about them, call the tool `recall_facts`.
5. If you do not find the answer in the documents, say you do not know.

Keep your answers short and simple.
"""

Read rule 1 again

"Never do the math in your head." That sentence exists because without it, the model happily answers 12 × 8 from memory and skips the tool. It is usually right — and then one day it is quietly wrong, and you have a calculator sitting unused two files away.

Rule 2 does the same job for facts: answer using ONLY what those documents say. That single line is the difference between a support bot and a bot that invents refund policies.

Memory gets injected here

The prompt is not a fixed string. Everything in the long-term memory file is appended before every question, so the bot starts each turn already knowing the user.

backend/prompts.py
def build_system_prompt(long_term_facts):
    if not long_term_facts:
        return SYSTEM_PROMPT + "\nLong term memory: (empty)\n"

    lines = ""
    for fact in long_term_facts:
        lines = lines + "- " + fact + "\n"

    return SYSTEM_PROMPT + "\nLong term memory:\n" + lines

So the model literally sees this at the top of every request:

what actually gets sent
Long term memory (things you already know about the user):
- The user's name is Nitish.
- The user lives in Pune.
- The user prefers short answers.
Change behaviour here first

Before you reach for fine-tuning, more tools, or a bigger model: edit the prompt. It costs nothing, takes ten seconds, and fixes most "the bot did something silly" complaints. Add a numbered rule, restart, try again.

The cost nobody mentions

The system prompt is re-sent on every request, and you pay for those tokens every time. A 2,000-word prompt on a chatty bot is a real bill. Keep rules short. Keep memory pruned. Long prompts are a recurring charge, not a one-off.

04

Tools

A tool is a normal Python function with a decorator on top. The hard part is not the code. It is the sentence underneath the def.

The smallest possible tool

backend/tools/math_tools.py
from langchain_core.tools import tool


@tool
def add(a: float, b: float) -> float:
    """Add two numbers together. Use this for any addition."""
    return a + b


@tool
def multiply(a: float, b: float) -> float:
    """Multiply two numbers. Use this for any multiplication."""
    return a * b


@tool
def divide(a: float, b: float) -> str:
    """Divide number a by number b. Use this for any division."""
    if b == 0:
        return "Error: cannot divide by zero."

    return str(a / b)

Three things the model reads

1
The function name
multiply. This is how the model refers to it. Name it what it does, in plain English.
2
The docstring
This becomes the tool description. It is not a comment for humans. The model genuinely reads this sentence to decide whether to use your tool.
3
The type hints
a: float, b: float tells the model what arguments to send, and LangChain validates them before your function runs.
This happened to us while building

The first version of the percentage tool was percentage(part, whole) — "what percent is 15 of 200?" = 7.5. But users ask "what is 15% of 200?" = 30.

The model called the tool, got 7.5, decided that looked wrong, ignored it and answered 30 from its own head. A silent, confident contradiction. The fix was not smarter code — it was renaming the tool and rewriting one sentence:

the fix — same maths, better description
@tool
def percent_of(percent: float, number: float) -> float:
    """Calculate a percentage of a number.
    Use this for questions like 'what is 15 percent of 200' or
    'give me 20% discount on 500'.
    Here percent=15 and number=200, and the answer is 30."""
    return (percent / 100) * number

Note the example inside the docstring. When a tool is even slightly ambiguous, put a worked example in the description. It is the cheapest accuracy fix available.

Tools do not have to be maths

backend/tools/text_tools.py
@tool
def get_current_time() -> str:
    """Get today's date and the current time.
    Use this when the user asks about date or time."""
    return datetime.now().strftime("%Y-%m-%d %H:%M:%S")

A model has no clock. Without this tool it will confidently tell you the wrong date. Four lines of Python fix a problem no amount of prompting can.

What makes a good tool

does one thing
Separate add and multiply beat one calculate(expression). Small tools are easier for the model to choose correctly.
returns text the model can read
Return a sentence or a simple number, not a nested object. The result goes straight into the model's context.
fails politely
"Error: cannot divide by zero." beats an exception. The model can read that and recover; a traceback kills the run.
has an unmistakable name
If two tools could plausibly answer the same question, the model will sometimes pick the wrong one. That is your fault, not its.
Your tool works perfectly but the model never calls it. Where do you look first?
The docstring and the name. Tool selection happens entirely from the name plus that one description sentence. If the model cannot tell from those two things that your tool answers the question, it will not call it. Rewrite the description to mention the words users actually type.

The Tool Registry

One file that collects every tool in the application. It is also, quietly, your permission system.

The whole file

backend/tools/registry.py
from tools import data_tools, math_tools, memory_tools, text_tools


ALL_TOOLS = [
    # --- math tools ---
    math_tools.add,
    math_tools.subtract,
    math_tools.multiply,
    math_tools.divide,
    math_tools.percent_of,

    # --- data tools (our JSON corpus) ---
    data_tools.search_knowledge_base,
    data_tools.get_document,
    data_tools.list_topics,

    # --- long term memory tools ---
    memory_tools.remember_fact,
    memory_tools.recall_facts,
    memory_tools.forget_everything,

    # --- small helper tools ---
    text_tools.get_current_time,
    text_tools.count_words,
    text_tools.to_uppercase,
    text_tools.reverse_text,
]

Why bother, when it is just a list?

  • The agent imports one thing. from tools.registry import ALL_TOOLS. Not five imports scattered through agent.py.
  • You can see the agent's entire capability in one screen. Someone asks "what can this bot do?" — you show them this file.
  • It is the permission boundary. A tool that is not in this list cannot be called, no matter what the model says. Comment out a line and that ability is gone.
  • Different agents, different lists. A read-only support bot gets the search tools; an admin bot gets more. Same functions, different registries.

Adding a tool takes two edits

step 1 — write the function anywhere in tools/
@tool
def square(number: float) -> float:
    """Multiply a number by itself.
    Use this when the user asks for a square."""
    return number * number
step 2 — add one line to the registry
ALL_TOOLS = [
    math_tools.add,
    math_tools.square,   # <-- that is the whole wiring
    ...
]

Restart the server. The agent can use it. Nothing else in the codebase changes.

Print the registry to explain it

registry.print_tools() — run this live
TOOL REGISTRY - 15 tools available

  * add
      Add two numbers together. Use this for any addition.
  * search_knowledge_base
      Search the CloudDesk company documents for a topic...
  * remember_fact
      Save one fact about the user into long term memory...

This is very close to what the model itself receives. Showing it makes the whole thing click: the model is choosing from a menu, and this is the menu.

Every tool costs tokens

All 15 descriptions are sent with every request, whether or not they get used. Fifteen is comfortable. Fifty starts to hurt your bill and your accuracy — the more similar options there are, the more often the model picks a neighbour. When a registry gets big, split it per agent rather than growing one giant list.

06

How Tool Calls Travel

The single most important slide in this deck. An agent is a list of messages that keeps growing — and a tool call is just three of those messages in a row.

There are only four kinds of message

SystemMessage
The rules. Our system prompt. Sent first, every time.
HumanMessage
What the user typed.
AIMessage
What the model said. If it wants a tool, the text is empty and it carries a tool_calls list instead.
ToolMessage
What your Python function returned. This gets sent back into the model as a new message.

"What is 12 times 8?" — the real sequence

               # the model ASKS. it has not computed anything.

               # OUR python function ran and produced this

AIMessage      text = "12 times 8 is 96."
               tool_calls = []
               # no tool calls means the loop stops here

How the loop knows to stop

One condition, and it is beautifully simple:

the stopping rule
if not reply.tool_calls:
    return reply.text     # nothing more to do — this is the answer

An AIMessage with tool calls means "keep going". An AIMessage without them means "I'm done". That is the entire control flow.

Reading it out of the result

trace.py walks the finished message list and labels each one. This is the whole function that produces our phase panel:

backend/trace.py
for message in messages:
    kind = message.__class__.__name__

    if kind == "HumanMessage":
        steps.append({"phase": "USER MESSAGE", ...})

    elif kind == "AIMessage":
        # case 1: the model wants tools
        if message.tool_calls:
            for call in message.tool_calls:
                steps.append({
                    "phase": "TOOL CALL",
                    "title": "Model asked for tool: " + call["name"],
                    "detail": "arguments = " + str(call["args"]),
                })
        # case 2: final text answer
        else:
            steps.append({"phase": "FINAL ANSWER", ...})

    elif kind == "ToolMessage":
        steps.append({"phase": "TOOL RESULT", ...})

Two tools in one turn

The model can ask for several tools at once. "Remember I live in Pune and I like Python" produces two tool calls in a single AIMessage, and they run at the same time:

real output from our terminal
[3] TOOL CALL    remember_fact   args = {'fact': "The user's name is Nitish."}
[4] TOOL CALL    remember_fact   args = {'fact': 'The user lives in Pune.'}
[5] TOOL RESULT  Saved to long term memory: The user's name is Nitish.
[6] TOOL RESULT  Saved to long term memory: The user lives in Pune.
[7] FINAL ANSWER I've remembered that your name is Nitish and you live in Pune.
This bit us for real

Because those two tool calls run at the same time, both read the JSON file, both appended one fact, and both wrote the file back. One fact vanished. A reader could even catch a half-written file.

The fix is on slide 08. But note the lesson now: the moment tools can run in parallel, every shared file or counter becomes a race.

Where does the string "96.0" physically come from?
Your function returned it. multiply(12, 8) ran on your machine and returned the float 96.0. LangChain wrapped it in a ToolMessage and sent it back to the model, which then wrote a sentence around it. The number is real; only the sentence is generated.
07

Short Term Memory

The model remembers nothing. Not one word. Every follow-up question works only because we re-send the entire conversation, every time.

The entire implementation

backend/short_term_memory.py
# session_id  ->  list of langchain messages
CHAT_HISTORY = {}

# keep the last 10 messages (about 5 questions and 5 answers)
MAX_MESSAGES = 10


def get_history(session_id):
    if session_id not in CHAT_HISTORY:
        CHAT_HISTORY[session_id] = []

    return CHAT_HISTORY[session_id]


def save_history(session_id, messages):
    CHAT_HISTORY[session_id] = messages[-MAX_MESSAGES:]

That is it. A dictionary. No database, no framework, no vector store. Short term memory is a Python dict and people are always surprised by that.

How it gets used

backend/agent.py
# take everything said earlier in this conversation
history = short_term_memory.get_history(session_id)

# put the new question at the end
messages_to_send = history + [HumanMessage(content=user_message)]

result = agent.invoke({"messages": messages_to_send})

Why "and what about the Business plan?" works

what the model receives on the second question
SystemMessage  "You are Bia..."
HumanMessage   "how much is the Team plan?"        # old
AIMessage      "The Team plan costs 30 dollars..."   # old
HumanMessage   "and what about the Business plan?"   # new

The word "Business plan" only makes sense next to the previous exchange. Delete the history and the bot has no idea what you are asking about.

The mental model that fixes everything

An LLM is a pure function. Same input, same output. It has no memory between calls at all. Everything that looks like memory is you, resending text.

So "the bot forgot" is never a bug in the model. It is a bug in what you chose to resend.

Why we cut it at 10 messages

Every message in the history is re-sent and re-charged on every turn. A conversation that runs all day would grow forever, get slower, cost more, and eventually blow past the context window.

messages[-MAX_MESSAGES:] keeps the last 10 and drops the rest. Crude, and completely fine for a demo. Real systems summarise the dropped part instead of binning it.

What we deliberately do not store

backend/agent.py
# we save only the question and the answer,
# not every tool message, to keep the history small
new_history = history + [
    HumanMessage(content=user_message),
    all_messages[-1],
]
short_term_memory.save_history(session_id, new_history)

The tool calls and tool results from old turns are thrown away. The model does not need to re-read "96.0" from ten minutes ago — it only needs the conclusion.

It dies with the process

CHAT_HISTORY lives in RAM. Restart uvicorn and every conversation is gone. That is the entire difference between short term and long term memory — and it is why the next slide writes to a file.

Your bot "forgets" what was said two questions ago. Which file is the bug in?
short_term_memory.py. With MAX_MESSAGES = 10 you keep about five exchanges; anything older is dropped before it is ever sent. The model never saw it, so it cannot have forgotten it. Raise the limit, or summarise what you drop.

The tool that writes it

This is where it gets interesting. We never parse the user's sentence looking for the word "remember". The model decides, and it decides by reading this docstring:

backend/tools/memory_tools.py
@tool
def remember_fact(fact: str) -> str:
    """Save one fact about the user into long term memory,
    so it is remembered forever.
    Use this whenever the user says 'remember ...' or tells you
    something personal that will be useful later, like their name,
    their city, or what they like.
    Write the fact as a short full sentence,
    for example 'The user lives in Pune'."""

    long_term_memory.add_fact(fact)
    return "Saved to long term memory: " + fact

Notice it also rewrites the phrasing. You type "remember I live in Pune"; the model stores "The user lives in Pune." — because the docstring asked for a full sentence. That is prompt engineering happening inside a tool description.

Writing it safely

Remember the race from slide 06 — two remember_fact calls at once, one fact lost. Two small changes fix it, and both are worth explaining:

backend/long_term_memory.py
# the model can ask for two tools AT THE SAME TIME.
# this lock makes sure only one of them writes at a time.
LOCK = threading.Lock()


def save_memory(memory):
    # write to a temp file, then rename. renaming is one single
    # step, so nobody can ever read a half written file.
    temp_file = MEMORY_FILE + ".tmp"

    with open(temp_file, "w") as f:
        json.dump(memory, f, indent=2)

    os.replace(temp_file, MEMORY_FILE)


def add_fact(fact):
    with LOCK:
        memory = load_memory()
        memory["facts"].append({
            "fact": fact,
            "saved_at": datetime.now().strftime("%Y-%m-%d %H:%M:%S"),
        })
        save_memory(memory)

Before: 20 parallel writes saved 1 fact. After: 20 out of 20. Six lines of difference.

The demo that lands

Open data/long_term_memory.json in the editor, side by side with the chat. Type "remember that I love cricket". Watch the file change while they look at it. Then restart the server, ask "what do you know about me?", and it still knows. That is the moment long-term memory stops being an abstract term.

Where this design runs out

Every fact is dumped into every prompt. At ten facts that is fine. At a thousand it is unaffordable and the important ones get lost in the noise.

Real systems store facts in a database, retrieve only the relevant ones per question, and expire or merge contradictions ("lives in Pune" vs "moved to Bangalore"). Our version has no idea one fact can replace another.

Answering From Our Own Data

The model has never heard of your company. Give it a search tool over your documents and it stops guessing.

The corpus is just a JSON list

data/corpus.json
[
  {
    "id": "doc-3",
    "title": "Refund Policy",
    "topic": "policy",
    "text": "Customers can ask for a full refund within 30 days
             of payment. Refunds are sent back to the original
             payment method and take 5 to 7 working days..."
  },
  ...
]

Ten documents about a fictional product. Swap in your own and the bot changes domain in one file.

The search tool

No embeddings. No vector database. We count how many words of the question appear in each document — and for a teaching demo it works remarkably well.

backend/tools/data_tools.py
@tool
def search_knowledge_base(query: str) -> str:
    """Search the CloudDesk company documents for a topic.
    Use this for any question about pricing, plans, refunds,
    policies, support, security, integrations or features."""

    documents = load_corpus()
    words = query.lower().split()
    results = []

    for doc in documents:
        haystack = (doc["title"] + " " + doc["topic"]
                    + " " + doc["text"]).lower()

        # how many words of the question appear in this doc?
        score = 0
        for word in words:
            if word in haystack:
                score = score + 1

        if score > 0:
            results.append({"score": score, "doc": doc})

    # best match first, keep the top 3
    results.sort(key=lambda item: item["score"], reverse=True)
    results = results[:3]

What comes back

the ToolMessage the model receives
Found 3 document(s):

[doc-3] Refund Policy
Customers can ask for a full refund within 30 days of payment...

[doc-9] How to Cancel an Account
To cancel, go to Settings, then Billing...

Plain text with the source id in front. The model reads it and writes an answer grounded in those words — and if you ask, it can cite doc-3.

This is RAG, with the scary parts removed

Retrieve
Find documents that match the question. Ours: word counting. Real: embeddings.
Augment
Put those documents into the model's context, as a ToolMessage.
Generate
Model writes the answer using only what it was given.

Everything a vector database adds is a better Retrieve step. The shape of the solution is identical — which is exactly why starting here makes the upgrade obvious later.

When word matching is not enough

Ask "how do I get my money back?" — no document contains those words, so our search finds nothing. Embeddings would match it to the refund policy by meaning.

That failure is worth demonstrating live. It shows exactly what problem a vector database solves, instead of the usual hand-waving.

The prompt rule that prevents invention

"Then answer using ONLY what those documents say." Plus: "If you do not find the answer in the documents, say you do not know."

Test it by asking something not in the corpus — "do you support Salesforce?". A good agent says it does not know. Without those two lines, it cheerfully makes something up.

The endpoint

backend/main.py
class ChatRequest(BaseModel):
    # this describes the JSON React must send us
    message: str
    session_id: str = "default"


@app.post("/chat")
def chat(request: ChatRequest):
    print("\n>>> API HIT: POST /chat")
    print(">>> message:", request.message)

    # give the work to the agent
    answer, steps = agent.run_agent(request.message, request.session_id)

    print(">>> API RETURNING the answer to React\n")

    return {
        "answer": answer,
        "steps": steps,
        "short_term_memory_size": len(...),
        "long_term_memory": long_term_memory.get_all_facts(),
    }

Eleven lines of real work. BaseModel means FastAPI validates the incoming JSON for you and returns a clear 422 if React sends rubbish — no manual checking.

React runs on port 5173, the API on 8001. Different ports mean different origins, and the browser blocks the request unless the server says it is allowed. allow_origins=["*"] is fine for a classroom and wrong for production — name your real domain there.

The restart trick

After saving a few facts, stop uvicorn and start it again. Ask "what did we just talk about?" — gone. Ask "what do you remember about me?" — still there.

Short term memory died with the process. Long term memory was on disk. Thirty seconds, and nobody confuses the two again.

01 · LangChain

What it is. The high-level toolkit — models, prompts, tools, output parsers, and a ready-made agent loop. It is what we used all afternoon. create_agent(model, tools, system_prompt) and you have a working agent.

Use it when one agent with a bag of tools genuinely solves the problem — which is more often than people expect. Do not skip past it because it looks too simple.

langchain — the whole agent
from langchain.agents import create_agent
from langchain_openai import ChatOpenAI

agent = create_agent(
    ChatOpenAI(model="gpt-4o-mini", temperature=0),
    ALL_TOOLS,
    system_prompt=SYSTEM_PROMPT,
)

result = agent.invoke({"messages": [HumanMessage(content="...")]})

Example projects

  • Internal helpdesk bot — searches your policy documents, answers HR and IT questions, escalates by creating a ticket.
  • Customer support bot over product docs — exactly this project, with your corpus swapped in.
  • Database question answering — a run_sql tool over a read-only connection, plus a schema description tool.
  • Personal assistant — calendar, email search, weather. Many small tools, one loop.
Where it stops

The model chooses the path every run, so you cannot promise "step 3 always happens after step 2". There is no built-in way to pause for a human and resume tomorrow. The moment you need a guarantee about the order, you have outgrown it.

02 · LangGraph

What it is. From the same team, one level lower. You describe your process as a graph: nodes are steps, edges are what happens next, and there is a shared state object flowing through it. Conditional edges give you branching; a checkpointer gives you persistence.

Use it when the process must be reliable and inspectable — approvals, retries, escalation, or anything that runs longer than one HTTP request.

langgraph — you draw the path
from langgraph.graph import StateGraph, END
from langgraph.checkpoint.memory import MemorySaver

def check_policy(state):    # plain python functions
    ...
def auto_approve(state):
    ...
def ask_human(state):
    ...

graph = StateGraph(RefundState)
graph.add_node("check", check_policy)
graph.add_node("auto", auto_approve)
graph.add_node("human", ask_human)

graph.set_entry_point("check")

# small refunds go through, big ones wait for a person
graph.add_conditional_edges("check", route_by_amount, {
    "small": "auto",
    "large": "human",
})
graph.add_edge("auto", END)

# the checkpointer is why this can pause and resume later
app = graph.compile(checkpointer=MemorySaver(),
                    interrupt_before=["human"])

Example projects

  • Refund approval — under ₹5,000 auto-approve, above that stop and wait for a manager, then resume days later at the same point.
  • Loan or KYC processing — extract, validate, check rules, escalate on failure, with a full audit trail of every state change.
  • Deep research assistant — search, read, judge "is this enough?", loop back for more, then write. The loop is a real cycle in the graph.
  • Order-to-shipment flow — retries on a flaky inventory API, a compensating step when payment fails.
The honest trade

You write more code and you draw your own diagram. In exchange, you can answer "what will this do on Tuesday?" — which is exactly the question compliance, finance and your on-call rota all ask. Control costs design effort. That is the deal.

03 · CrewAI

What it is. A team metaphor. You define agents with a role, a goal and a backstory, give each one a task, and the crew runs them in sequence (or with a manager agent delegating). The output of one task feeds the next.

Use it when the work genuinely splits into different jobs a human team would divide — and when a readable, role-shaped script is worth more than fine control.

crewai — a team with roles
from crewai import Agent, Task, Crew

researcher = Agent(
    role="Market Researcher",
    goal="Find recent facts about {topic}",
    backstory="You dig through sources and never invent numbers.",
    tools=[search_tool],
)

writer = Agent(
    role="Report Writer",
    goal="Turn research notes into a clear one page report",
    backstory="You write plainly for busy executives.",
)

research_task = Task(
    description="Research {topic}. List the key facts with sources.",
    expected_output="A bullet list of facts",
    agent=researcher,
)

write_task = Task(
    description="Write a 300 word report from the research.",
    expected_output="A short report",
    agent=writer,
    context=[research_task],      # feeds task 1's output in
)

crew = Crew(agents=[researcher, writer], tasks=[research_task, write_task])
print(crew.kickoff(inputs={"topic": "electric cars in India"}))

Example projects

  • Market research report — researcher gathers, analyst finds the pattern, writer produces the document. The classic CrewAI demo, and it genuinely works.
  • Content pipeline — SEO planner → draft writer → editor → fact checker, producing a finished blog post.
  • Resume screening — one agent extracts skills, one scores against the job description, one drafts the interview questions.
  • Competitor teardown — an agent per competitor running in parallel, then a synthesiser that merges the findings.
The multi-agent tax

Four agents means at least four times the tokens and four times the latency. Every handoff is a chance to lose detail.

Before splitting into a crew, ask honestly: would one agent with good tools have done this? Very often the answer is yes, and the crew exists because it looks impressive in a demo rather than because the work needed it.

04 · AutoGen

What it is. Microsoft's multi-agent framework, built around agents that hold a conversation with each other. Its signature move is the write–run–critique loop: one agent proposes code, another executes it, a third reviews, and they iterate until a stop condition fires.

Use it when the answer improves by being argued over — code that must actually run, analysis that needs a sceptic, a draft that needs a critic.

autogen — agents that talk to each other
from autogen_agentchat.agents import AssistantAgent
from autogen_agentchat.teams import RoundRobinGroupChat
from autogen_agentchat.conditions import TextMentionTermination
from autogen_ext.models.openai import OpenAIChatCompletionClient

model = OpenAIChatCompletionClient(model="gpt-4o-mini")

coder = AssistantAgent(
    "coder",
    model_client=model,
    system_message="Write python. Fix it when the reviewer objects.",
)

reviewer = AssistantAgent(
    "reviewer",
    model_client=model,
    system_message="Review the code. Say APPROVE when it is correct.",
)

# they take turns until 'APPROVE' appears, or 8 turns pass
team = RoundRobinGroupChat(
    [coder, reviewer],
    termination_condition=TextMentionTermination("APPROVE"),
    max_turns=8,
)

await team.run(task="Write a function that finds duplicate rows in a CSV")

Example projects

  • Data analysis assistant — one agent writes pandas code, an executor actually runs it, and errors go back for a fix. The loop keeps going until the chart appears.
  • Automated code review pair — an implementer and a sceptic argue until the tests pass.
  • Hard problem solving — a solver plus a dedicated critic whose only job is to find the flaw. Measurably better than one agent alone on maths and logic.
  • Research prototyping — trying out agent conversation patterns before committing to a design.
Watch the meter

Conversational agents are the easiest way to accidentally spend money. Two agents that both think they should have the last word will happily run to your turn limit, every time.

Always set a termination condition and a max turn count, and never let an execution loop run untrusted generated code outside a container.

Version note

AutoGen was substantially rewritten at v0.4 — the modern API lives in autogen-agentchat and is async, which is why you see await above. Older tutorials show a very different UserProxyAgent style from v0.2. Microsoft has also been converging AutoGen with Semantic Kernel into a single Agent Framework, so check the current docs before starting a new project rather than trusting a blog post.

And the option nobody sells you

No framework at all. The OpenAI or Anthropic SDK gives you tool calling directly. The agent loop is about twenty lines — you saw it on slide 02. No abstraction to learn, no version churn, complete visibility.

This is a genuinely good choice for a small production bot with five tools. You give up prebuilt memory, retries and streaming helpers, and you write those yourself. Sometimes that is cheaper than learning where a framework hid them.

A bank wants an agent that processes refunds, but anything above ₹50,000 must be approved by a manager who may not respond until tomorrow. What do you reach for?
LangGraph. Two requirements decide it: a hard rule about which path is taken at a threshold, and the ability to stop mid-process and resume days later. Conditional edges give you the first, the checkpointer gives you the second. A crew or a conversation gives you neither guarantee — and this is money, so "usually right" is not a specification.

Which One, When

A decision path you can actually follow on Monday, and the order to build things in.

Work down this list and stop at the first yes

1
Would a single prompt do it?
Summarising, classifying, rewriting. Then you do not need an agent at all. One API call is cheaper, faster and cannot loop.
2
Do you know the exact steps in advance?
Then write a normal Python function that calls the model a few times. A for loop you wrote beats an agent that might improvise.
3
Does it need to look things up or take actions, in an order you cannot predict?
Now you need an agent. Start with LangChain — one agent, a handful of tools. This project.
4
Does it need approvals, retries, branching, or to resume tomorrow?
Move to LangGraph. Same ecosystem, so tools and prompts come across.
5
Does the work split into clearly different jobs?
CrewAI for a role pipeline, AutoGen when the agents need to critique each other. Only after a single agent has visibly failed.
The rule that saves the most money

One good agent with well described tools beats a team of mediocre ones almost every time.

Multi-agent is a solution to a specific problem — one context window cannot hold the whole job, or you genuinely need an independent critic. It is not a way to make a system smarter. Reach for it when you can name the failure it fixes.

What to build first, in order

#BuildWhy it comes first
1Tools with excellent descriptionsMost agent failures are tool selection failures. This is where accuracy lives.
2A tool registryYour capability list and your permission boundary, in one file.
3Tracing — print every phaseWithout it you are debugging blind. It is what trace.py exists for.
4Step and cost limitsOne runaway loop can cost more than a week of your salary.
5Short term memoryFollow-up questions are most of real usage.
6A test set of 20 real questionsSo you can tell whether today's prompt change helped or hurt.
7Long term memoryGenuinely useful, and genuinely optional. Later than people think.
8Multi-agentLast. Only when you can point at what a single agent failed to do.

What this project deliberately left out

  • Streaming — answers arrive all at once. Real chat UIs stream tokens as they generate.
  • A step limit — nothing stops a loop that never settles. Add a max-iterations cap before production.
  • Authentication — session_id is whatever the browser sends. Anyone could read anyone's memory.
  • Real retrieval — word counting, not embeddings.
  • Error handling around the model call — a timeout or rate limit will surface as a 500.
  • Evaluation — no test set, so "did that prompt change help?" is currently a matter of opinion.

Each of those is a good exercise. They are missing on purpose: every one of them, added now, would hide the idea we are trying to teach.

The sentence to leave with

An agent is a model, a list of tools, and a loop that keeps going until the model stops asking for things.

Frameworks differ in how much of that loop they hand back to you. Start with the one that hands you the least, and only take control back when something breaks.

Your one-agent support bot is right 85% of the time. What is most likely to move the number?
Read the failures. They almost always cluster: a tool nobody could pick from its description, a question whose answer is not in the corpus at all, a prompt rule the model reads differently than you meant. Every one is a cheap targeted fix. Adding agents multiplies your cost and adds handoff failures on top of the ones you already have — without ever telling you what went wrong.
